# LitePay

面向独角数卡的 BEpusdt 收银台网关。付款人在同一个收银台依次选择 Binance 或 OKX、USDT 或 USDC，再按锁定的精确金额完成站内转账。网关并行确认两个平台的到账记录，成功后向商户发送 BEpusdt 结果通知。

## 工作方式

1. 独角数卡通过 `POST /api/v1/order/create-order` 创建订单。
2. LitePay 返回 `payment_url`；同一商户订单号下未过期的待支付订单会原样复用，不延长原有效期，也不占用金额档位。
3. 付款人选择平台与币种后，订单原子锁定收款 UID 和应付金额。
4. Binance 与 OKX 只确认各自被选中的站内转账，不读取链上充值。
5. 支付成功后发送 `status=2` 通知；本地订单在支付窗口和宽限期结束后发送 `status=3`。
6. 独角取消订单时调用 `POST /api/v1/order/cancel-transaction`，网关停止确认；取消由商户发起，不再发送与之冲突的 `status=3`。原金额保留至原支付窗口和宽限期结束，防止迟到转账误入其他订单。
7. 同号订单已过期、已取消或被替换时，旧订单会静默退役；新订单不会继承旧有效期，旧订单未发送的回调也会被丢弃。

## 独角数卡配置

| 配置项 | 值 |
|---|---|
| 支付渠道 | BEpusdt |
| 网关地址 | 本站域名，不带接口路径 |
| API Token | 从后台接入页复制；只能由系统生成和轮换 |
| 订单模式 | 收银台 |
| 交互模式 | 跳转 |
| 法币 | USD |
| 币种 | 可留空，或填写 `USDT,USDC` |

## 收款平台

Binance 与 OKX 均使用 UID 站内转账。API Key 只授予读取权限，并配置服务器 IP 白名单；不要开启交易或提现权限。

- Binance 读取 `/sapi/v1/pay/transactions`，只接受 `PAY`、`C2C` 正数收入，并校验 `receiverInfo.binanceId`、币种和精确金额。退款、出款和负数流水不会入账；Pay ID 不参与展示或校验。轮询前会通过 `/api/v3/account` 校验 API 账户 UID 与收款 UID 一致。
- OKX 读取 `/api/v5/asset/deposit-history`，通过请求参数 `type=3` 查询站内转账，只接受 `state=2` 且具有 `fromWdId` 的成功记录；响应未返回 `type` 时使用 `fromWdId` 识别内转。`type=4` 的链上充值不会入账。
- 收银台只展示和复制收款 UID，不生成静态收款二维码；付款金额、币种和 UID 都是核心信息。
- 收银台按所选平台切换品牌色；Binance 使用品牌黄，OKX 使用黑白品牌色，并支持浅色与深色主题。
- OKX 充值记录按官方时间游标自动翻页，每轮最多读取 20 页，不依赖进程内游标。

## 金额与确认

结算法币固定为 USD，USDT / USDC 按 1:1 计，不提供汇率功能。应付金额由 USD 订单金额加小额尾差得到。到账采用修约匹配（四舍五入）：按订单锁定时的固定小数位（包含尾零）修约实际到账金额，修约后一致即确认。后续配置变化不会改变已有订单的匹配、展示和回调精度。

- 同一平台和币种内，精确金额唯一；结束、取消或重选后的旧金额仍保留到原支付窗口和宽限期结束。
- Binance 与 OKX 的金额档位互相独立。
- 同商户订单号只保留一张可继续支付的订单；旧订单被替代后不会发送迟到的过期回调，避免关闭商户的新订单。
- 订单到期后在宽限期内仍确认截止前发出的转账；仅接受锁定收款方式后、到期前发生的转账。宽限结束才发送过期通知。
- 有待确认支付的订单时，不能更换收款凭据、UID、启用币种或宽限期；切换金额精度需等待同通道旧精度的金额占用全部结束。
- 后台可以人工标记已支付、重发结果通知或提前结束收银台。提前结束只关闭用户界面，订单仍按原支付窗口和宽限期确认已发生的转账，宽限结束才发送过期通知。

支付成功通知只有在 HTTP 2xx 且正文精确为 `success` 或 `ok`（不区分大小写）时才视为送达。独角数卡 Next 返回 `success`，官方 BEpusdt 接收方通常返回 `ok`。过期通知按 BEpusdt 官方协议要求 HTTP 2xx，但明确的 `fail` 正文会记为失败。

独角数卡 Next 的成功回调必须使用 `status=2`。当前上游 BEpusdt 适配器会拒绝 `status=3`，即使 HTTP 为 200 也返回 `fail`；因此后台“结束本地订单”能停止网关监听并记录通知结果，但不能保证同步关闭独角数卡订单。独角数卡主动取消时则调用 `cancel-transaction`，取消本身就是终态，网关不再额外发送过期通知。

## 配置

`config.yaml` 只保存启动参数：监听地址、数据库、后台登录和日志级别。业务配置全部保存在 SQLite，并在 `/admin/settings` 修改后立即生效。应用不读取 `.env` 或环境变量；部署脚本只从本机 `.env` 读取 SSH 与后台登录凭据。

```bash
cp config.example.yaml config.yaml
go run . -config config.yaml
```

首次启动后登录 `/admin/settings`，填写交易所只读密钥与收款 UID。API Token 由系统随机生成，在 `/admin/integration` 查看；需要更换时点击“生成新 Token”，旧值会立即失效。

根地址不再展示网关介绍或后台入口。在后台「设置 → 管理员 → 访问入口」可修改商店跳转地址和后台前缀，输入当前密码后保存，立即生效并跳到新入口重新登录。旧入口立即返回 404；设置保存在 SQLite，重启不会丢失。

首次安装也可在启动配置中设置初始值：

```yaml
server:
  store_url: "https://shop.example.com"
admin:
  path: "/workspace-your-random-suffix"
```

直接修改启动文件需重启；后台已保存的设置优先于启动文件。其余启动配置保持原值。`store_url` 留空时根地址返回 404，不能指向网关本站。`admin.path` 留空兼容旧 `/admin`；自定义后旧 `/admin` 返回 404，不会跳转或提示新入口。路径必须是单层、3~96 位字母数字、下划线或连字符，不能占用系统路由。登录、会话 Cookie、导航、表单与跳转均使用新前缀。路径隐藏不代替密码、限流或 CSRF；请保存入口地址，勿发布到公共仓库。支付 API、收银台、健康和就绪地址不变。

## 部署

```bash
./scripts/deploy.sh
```

部署脚本会编译 Linux ARM64，在远端临时目录校验配置并预构建镜像；只有构建成功后才切换容器，业务数据卷始终保留。健康检查通过后才清理历史 LitePay 回滚归档，开发状态不创建新备份。容器入口设置 `umask 077`，保证 SQLite 主库及 WAL/SHM 文件仅进程用户可读写。


回调地址必须可以从公网直接访问；内网、回环、链路本地和保留地址被拒绝，HTTP 重定向不会跟随。下单 `amount` 范围为 `(0, 1000000000]`，`timeout` 为 0（默认值）或 120~86400 秒。

### 用户自行查款补单

选择付款方式满 1 分钟仍未确认时，收银台显示「已付款但未确认？提交转账编号查款」。金额沿用当前订单，不由付款人重新填写。Binance 填付款详情中的交易编号或订单编号（只匹配 API 实际返回的 `transactionId` / `orderId`，不推测二者关系）；OKX 填付款方站内转账的提现编号（`fromWdId`），不是收款侧 `depId` 或链上哈希。

服务器通过收款账户的只读 API 核实，沿用原流水唯一键和核销事务，再由原回调任务通知商户。Binance 补查订单付款窗口并精确比对原始交易编号，保留父事件与明细身份；多明细事件保留证据并交人工处理；OKX 使用 `fromWdId` 过滤，并以返回的 `depId` 认领。查款不会推进扫描游标或消除历史缺口，也不强制重发回调。已确认但商户未确认回调时，结果页明确提示两者的区别。

每单至少间隔 60 秒、最多 10 次实际查款，限制持久化；每平台的自助查询另有 30 秒间隔，与轮询共享客户端和串行互斥，单次最长 8 秒，Binance 最多 4 次请求（含 UID 核验、校时及重试）；自动扫描等待时优先让路。用户提交的编号独立记录于 `payment_inquiries`，不是交易所到账证据；后台订单详情展示最近编号、次数和结果。API 未返回记录时不能凭编号入账。错金额、币种、时间、账户、退款、链上充值、已被其他订单认领的流水、存在歧义及已最终关闭订单均不自动补单。已过付款窗口但尚待补扫的订单，可在刷新后的订单结果页查款；仅付款时间在原锁定窗口内且其余校验通过时允许核销。

四种平台/币种组合已通过模拟交易所 HTTP → 用户提交编号 → 原子核销 → 签名回调 → 商户验签/幂等交付测试。实际 App 显示编号与 API 字段的对应关系仍需真实小额付款样本验收。

### 第七阶段的交易身份与辅助对账

自动扫描和主动查款统一使用事件级闸门：同一父资金事件最多支付一张订单。Binance 保留 API 原始 `transactionId`、可选 `orderId` 及明细标识；单明细与无明细返回使用同一父事件核销键，多资产或多明细不自动核销，不跨币种相加。OKX 仅以 `depId` 生成 `okx:depId`，`fromWdId` 只作查询编号；缺少 depId 或同一发送编号存在多条充值记录时保持待人工核对。曾发现的歧义持久保存，不能通过接口返回结构变化消除。旧的合成 MANUAL 流水补单已禁用。

后台「接入信息 → OKX 辅助只读对账」可手动查询最近 24 小时 `type=72` 的资金账单，至少间隔 5 分钟；默认无自动轮询。账单分页按当前官方文档使用时间戳 after，以 billId 去重和检查冲突，饱和同毫秒边界无法前进时失败。billId 与 depId 不等价；金额和时间接近只列为候选，不证明关联。辅助证据不写 incoming_txs，不改变订单、回调或扫描游标。返回冲突、分页不完整或 API 错误会标记人工核对。

Binance 对 -1021 只同步 `/api/v3/time` 并重试一次；鉴权、限流、网络、超时、解析、业务拒绝和不完整历史有安全分类。所有签名请求共享间隔与限流退避；历史补查有 30 秒/64 次请求预算和原分窗完整性检查。错误不回显原始响应、账户资料或签名 URL，`/api/v3/account` UID 校验保留。

SQLite 升级步骤及历史记录处理见 [事件身份迁移](docs/sqlite-event-identity-migration.md)。本轮没有访问生产或真实资金。
