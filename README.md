# LitePay

LitePay 是一个轻量级加密货币支付收银台网关，基于 Go、Gin 与 SQLite 构建，对外提供兼容 BEpusdt 的标准 JSON API。

系统支持将商户的 USD 计价订单转换为 **Binance Pay（币安支付）**、**OKX 站内转账**、**Bybit 站内转账**及 **Bitget 站内转账**支付，支持的付款币种包括 USDT 与 USDC。

> [!NOTE]
> **当前状态**：系统已在生产环境接入商城（dujiao-next）稳定运行。根据生产服务器实测订单与运行日志：
> - **已通过生产真实资金闭环验证**：**Binance Pay（USDT 5 笔、USDC 4 笔）** 与 **OKX 站内转账（USDT 3 笔）** 共 12 笔真实订单（金额区间 `0.52`～`3.51` USDT/USDC，覆盖基础整额与 `+0.01` 独占档位递增场景）均在到账后数秒内自动认领核销，商城异步回调 12 笔全部首轮（`attempt=1`）返回 `HTTP 200` 确认交付，零重试、零冲突；同时生产环境已实际验证 Binance 出账流水（`not_incoming_payment`）自动拒认、OKX 无匹配订单流水（`no_match`）保留证据不误领，以及 `dujiao_cancel_sync` 关单同步守护进程双向心跳与 15 笔取消意图同步。
> - **待执行真实资金付款验证**：新接入的 **Bybit 站内转账**与 **Bitget 站内转账**已在生产环境完成只读 API 凭据接入与后台持续轮询扫描（`scan_cursors` 正常推进无报错），尚未产生真实资金到账订单。验收流程详见 [小额真实付款人工验收清单](docs/acceptance-real-payment.md)。

## 开发运行

### 环境要求与本地启动

Go 最低版本以 [go.mod](go.mod) 为准。复制示例配置文件并启动服务：

```sh
cp config.example.yaml config.yaml
# 在 config.yaml 中设置管理员密码等必要项
go run . -config config.yaml
```

- **默认数据库**：SQLite 数据库位于 `data/litepay-dev.db`。
- **初始配置**：服务首次启动后，访问 `/admin/settings` 配置只读 API 凭据、收款 UID / 地址、开放币种及金额规则。
- **商户接入**：访问 `/admin/integration` 读取系统生成的 BEpusdt Token 及接入配置。
- **路径与跳转**：支持自定义管理后台路径前缀以及根路径跳转的商城地址。

### 权限与安全规范

- **API 凭据安全**：交易所 API 凭据**仅需只读查询权限**，严禁开启交易或提现权限。
- **运行模式**：生产环境默认启用 `server.production: true`，此时强制要求配置 HTTPS、商户回调域名白名单、bcrypt 哈希管理员密码（`$2a$`/`$2b$`/`$2y$`，且会话时长上限 72 小时）以及凭据加密主密钥；本地开发测试时须显式设置为 `false`（明文密码最短 12 位）。
- **敏感凭据加密**：数据库中的交易所 API Key/Secret、Passphrase 与 BEpusdt API Token 采用 AES-256-GCM 加密存储，主密钥通过 `server.master_key_file`、`LITEPAY_MASTER_KEY_FILE` 或 `LITEPAY_MASTER_KEY` 提供；接入页默认仅展示脱敏 Token，查看完整值须经 POST + CSRF 校验并记录审计日志。
- **机密隔离**：配置文件、主密钥文件与 SQLite 数据库包含敏感凭据，严禁提交至 Git 仓库。
- **数据库升级**：支持的数据库版本与加法迁移规则以 `internal/store/store.go` 中的 `Open` 为准，可通过 `PRAGMA user_version` 检查当前版本。升级前必须执行一致性备份与隔离验证；旧版二进制可能拒绝升级后的数据库。

- GRAM 收款配置、周期检测、Kraken 实时报价与到账核对：[GRAM 收款](docs/gram-payments.md)

## 核心处理

### 处理流水线

```
交易所 / Toncenter API 轮询
            ↓
       统一交易证据入库
            ↓
       精确条件匹配核销
            ↓
       SQLite 事务原子认领
            ↓
       商户异步回调通知
            ↓
    商户端确认 (2xx + success/ok)
```

### 金额精度与独占档位

- **微单位精度与防四舍五入**：内部金额使用整数微单位（6 位小数）存储。超出精度且非零的尾数直接拒绝，绝不进行四舍五入。
- **独占档位与区间约束**：应付金额向上对齐显示精度后分配独占档位。创建订单、向上对齐、档位冲突递增与重选四条路径，均严格约束在上游商城 float64 验签区间 `[0.0001, 1000000)` 内。若无合法可用档位，直接拒绝选择该付款方式，不截断、不调低金额，也不留下档位占用。
- **结算期占用**：金额档位持续保留至独立结算期结束；主动取消订单会立即停止自动认领。

### 平台流水解析与交易证据

- **交易唯一性约束**：交易以 `(provider, event_id)` 为唯一主键。到账证据与核销归属共用单表，订单归属具备数据库唯一约束。
- **Binance Pay 规则**：以 `transactionId` 为事件身份；实测响应包含纯数字 `orderId`（用户在 App 账单中可复制的订单号），后台参考号默认记录 `orderId`。仅核销收款方向（实测收款记录 `amount` 为正、出账记录为负且明细为正幅度）的 `PAY` / `C2C` 且回填收款 UID 的记录；总额与资产明细同时提供时必须全部精确解析且一致；单资产明细而总额为 0 等未定义形态直接拒绝自动认领；多个资产明细保留为歧义事件，禁止自动认领。
- **OKX 站内转账规则**：使用充值 `depId` 作为事件 ID、`fromWdId` 作为查询参考号，`ts` 为记录创建时间。仅 `state=2`（充值成功）且回填 `fromWdId` 的站内转账方可核销，其余状态保留为待确认证据；缺少 `depId` 或分页边界异常时整次查询失败，不推进扫描游标。
- **TON (GRAM) 规则**：每轮仅读取一页，证据与 LT/Hash 检查点原子提交，完整固定时间范围核对完成后方推进时间游标；服务宕机、超时或历史积压不会强迫每次从钱包最新记录重新开始。
- **精度溢出与契约保护**：交易所允许 8 位小数而支付系统仅处理 6 位：超出精度的记录保留为证据但拒绝自动核销，原始精确金额与原因存入 `RawAmount` 供后台人工核对，不阻断整次查询。若 API 响应契约不完整（缺少 `data`、`data` 非数组或 `data: null`），整次查询判定失败，不推进扫描进度。

### 原子核销与并发控制

- **严格核销条件**：要求平台、收款账户、币种、完整金额、付款时间窗口全部匹配，且存在唯一候选订单。
- **状态判定依据**：后台自动扫描通过 `store.Process` 核对到账；能否核销仅取决于订单与金额档位是否仍处于占用状态，与扫描器抓取到流水的时间无关。
- **无前端手动查单**：收银台不提供自助查单或手动提交流水入口；付款状态严格由后台自动扫描推进。
- **事务一致性**：已支付状态、资金归属及回调任务在同一 SQLite 事务内原子提交。后台仅展示证据与状态，不提供任何绕过交易唯一约束的强制支付入口。

### 订单生命周期与延期补偿

- **严谨过期机制**：订单仅在成功扫描覆盖完整付款窗口（含宽限期）之后方可过期；若交易所查询失败或扫描滞后，订单保持待付款状态，确保仍可能按时付款的订单不被永久关闭。
- **持久化补查任务**：付款窗口内出现唯一匹配订单的未确认到账时，持久化补查任务保留至该订单有效期结束后 48 小时；超期后转人工核对。
- **增量扫描与对账**：活跃付款与持久补查任务按平台配置间隔扫描；空闲时每分钟对账一次，订单取消后到账仍保留证据。增量扫描不跳过游标后的空白历史，未确认到账按原始时间专项补查。
- **独立付款指令（PaymentAttempt）**：每种收款方式生成独立 `PaymentAttempt`，保留对应地址、金额及原付款窗口；切回旧方式复用原金额，重选不解除旧尝试的收款责任。首笔唯一匹配到账核销订单，后续重复付款保留为额外到账证据（`additional_payment`）。

### 商户回调通知

- **租约隔离与重试**：商户回调任务通过递增尝试次数隔离过期的执行者，具备有限重试与结果日志审计。
- **确认契约**：仅当商户端返回 HTTP 2xx 且响应体为 `success` 或 `ok` 时，系统判定商户确认成功；商品发货的交付幂等由商城端自行保证。
- **通知范围**：系统仅发送 `status=2` 的支付成功回调，不发送超时过期通知。

### 健康检查与状态观测

- `/healthz`：验证底层 SQLite 数据库连通性。
- `/readyz` 与 `/readyz/providers/:provider`：检查数据库与商城取消同步状态，并要求已配置的支付平台最近扫描成功且进度无积压（无待付款订单的空闲期不要求游标绝对新鲜）。未鉴权调用仅返回 `{"ready":bool}`；详细 `providers`、`degraded` 与失败 `reason` 仅对已登录后台管理员或携带 `server.readiness_token` 只读探针令牌的请求返回。令牌配置后至少 16 字节，仅支持 `X-Readiness-Token`、`X-Probe-Token` 或 `Authorization: Bearer ...` Header；不接受 URL 查询参数。
- 后台可实时查看未归属事件、扫描错误及未确认回调；对存在歧义或订单最终关闭后的到账，系统完整保留证据并交由人工在商城与交易所间核对。

### 真实付款人工验收

Binance Pay（USDT / USDC）与 OKX 站内转账（USDT）已在生产服务器完成 12 笔真实资金付款与商城端到端回调交付验证；新增收款渠道（如 Bybit、Bitget）或变更收款账户前，请按 [小额真实付款人工验收清单](docs/acceptance-real-payment.md) 完成小额实测。

### 容器化与生产部署安全规范

- **非 root 运行**：Dockerfile 以非 root 用户（UID 10001）运行，内置 `config.production.yaml` 强制进行生产级安全校验。
- **容器探活**：镜像每 30 秒以 wget 请求 `http://127.0.0.1:8080/healthz`，超时 3 秒，连续失败 3 次标记为 unhealthy。修改容器内监听端口时，请同时覆盖 Docker 健康检查命令。
- **生产配置约束**：未填写 HTTPS `base_url` 或商户 `notify_hosts` 白名单时，容器直接拒绝启动。
- **文件挂载方式**：将配置完成的文件只读挂载至 `/app/config.yaml`，数据持久化目录挂载至 `/app/data`。`config.example.yaml` 仅用于显式的本地开发。
- **运维演练工具**：仓库提供 `scripts/payment_db.py` 用于一致性备份、完整性检查、数据恢复与离线演练；生产部署与版本回滚请严格参照 [支付运维](docs/operations.md) 执行。

主密钥须为随机 32 字节的 64 位 hex 或 Base64 编码，不接受 32 字符口令。可用 `openssl rand -hex 32 > master.key` 生成，再执行 `chmod 600 master.key`。生产模式拒绝 group/other 有权限的密钥文件，开发模式会警告；容器挂载文件需允许 UID 10001 作为所有者读取。

首次迁移会把明文与旧版密文升级为 `enc:v2:`，以字段名绑定 GCM AAD，并执行 WAL 截断和 VACUUM 清理旧页；启动时仍兼容读取 `enc:v1:`。

轮换主密钥时先停止服务，保存受保护的恢复备份并生成新密钥。将正常配置或 `LITEPAY_MASTER_KEY_FILE` 指向新文件后执行：

```sh
LITEPAY_MASTER_KEY_FILE=/run/secrets/new.key ./litepay -config config.yaml -rotate-master-key-from /run/secrets/old.key
```

该命令在单个事务内重新加密敏感设置、系统凭据及历史签名密钥，成功后退出；随后用新密钥正常启动。事务失败时数据库不变；若提示轮换已提交但清理失败，须使用新密钥重启以重试清理。保留旧密钥直到验证成功，并按备份保留策略保护仍依赖旧密钥的备份。


### 备份与恢复

数据库备份必须与主密钥分开保管，并分别限制访问权限。回滚旧备份时，必须使用创建该备份时的主密钥；轮换只更新当前数据库，旧备份仍需旧密钥才能解密。删除旧密钥前，请先确认所有仍需保留的备份都有可用的解密密钥。

完成凭据加密迁移后，应轮换交易所 API Key，并清理旧的明文备份；数据库内的清理不会自动清除外部备份。具体备份和恢复命令见[支付运维](docs/operations.md)。

## 平台配置与关闭订单

### 平台收款配置

- **分区管理**：后台设置页按 Binance、OKX、GRAM 分区展示与管理。
- **配置项统一校验**：各平台的收款 UID / 地址、API 凭据、开放币种及扫描间隔统一保存与核验。
- **安全留空**：密钥输入框留空默认保留原值；点击「清空本平台收款配置」仅重置当前选中平台。
- **兼容性迁移**：旧版共享币种配置在加载时会自动转换为各平台独立币种存储。

### 待付款订单关闭

- **后台手动关闭**：后台订单列表与详情页支持手动关闭待付款订单。
- **接口取消**：商户端可签名调用 `POST /api/v1/order/cancel-transaction`，支持传入 `trade_id` 或 `order_id`（同时传入时必须指向同一订单）。
- **资金防误领**：关闭操作会立即停止认领该订单的到账，并保留对应金额档位的冷却期；已支付订单严禁关闭。

### 独角数卡（Dujiao）关单同步工具

若独角数卡未实现向 BEpusdt 网关下发取消通知，可在独角数卡数据库所在服务器部署并运行 `scripts/dujiao_cancel_sync.py`：

- **运行机制**：每 5 秒只读轮询已取消且未支付的订单，使用支付渠道既有凭据签名请求指定网关，并将重试状态写入独立的 SQLite 数据库文件。
- **域名匹配防护**：配置的网关地址与付款链接域名必须严格匹配；脚本绝不修改独角数据库。
- **故障重试与审计**：遇到网络异常执行退避重试；检测到已支付冲突时记录日志供人工复核；网关订单不存在时重试 3 次后记录为缺失，不将其标记为关闭。

```sh
python3 scripts/dujiao_cancel_sync.py --database /path/to/dujiao.db --state /path/to/cancel-sync.db --gateway https://pay.example.com
python3 -m unittest discover -s scripts -p 'test_*.py'
```

### 生产回调与异常处理

- **回调白名单与重发**：生产环境须在 `server.notify_hosts` 中配置商户域名精确白名单并启用 HTTPS。回调重试耗尽或超时后到账挂起时，管理员可在核对商城发货状态并记录原因后手动重发通知。
- **48 小时迟到结算期与补单**：付款窗口关闭后保留 48 小时迟到首次可见结算期（防御性设计，非平台 SLA）。超出结算期后，管理员可在订单详情页申请历史补扫，待流水验证通过并确认商城未发货后执行补单；已取消订单不支持补单。
- **安全轮换与容量限制**：生产环境默认暂停 BEpusdt Token 轮换，需先完成商城端历史密钥验签兼容性验收。金额容量、重选限制与恢复规范详见 [支付运维](docs/operations.md)。
