# LitePay

开发阶段的 Binance / OKX 站内转账与 TON 主网 GRAM 收银台，使用 Go、Gin、SQLite，提供 BEpusdt JSON 接口。支持 USD 订单，付款币种为 USDT / USDC / GRAM，尚未完成真实付款与商城交付验收。

## 开发运行

使用 Go 1.26。复制 `config.example.yaml` 为 `config.yaml`，设置管理员密码，然后运行：

```sh
go run . -config config.yaml
```

默认数据库为 `data/litepay-dev.db`。首次启动后到 `/admin/settings` 配置只读 API 凭据、收款 UID、币种和金额规则；到接入页读取生成的 BEpusdt Token。可以自定义后台入口及首页商店跳转地址。API 凭据仅需读取权限，不启用交易或提现。生产启动默认 `server.production: true`，须配置 HTTPS 和回调主机白名单；本机开发需显式设为 false。

数据库版本与支持的加法升级范围以 `internal/store/store.go` 的 `Open` 为准，可用 `PRAGMA user_version` 检查实际数据库。升级前先做一致性备份和隔离验证；旧二进制可能拒绝升级后的数据库。配置及数据库包含密钥，不要提交到 Git。备份、恢复、演练与发布流程见 [支付运维](docs/operations.md)。

GRAM 的配置、定期检测、报价和到账核对见 [GRAM 收款](docs/gram-payments.md)。

## 核心处理

交易所 / Toncenter API → 统一交易证据 → 精确条件匹配 → SQLite 原子核销 → 回调任务 → 商户确认。

- 金额使用整数微单位（六位小数）；超过精度且非零的尾数直接拒绝，绝不四舍五入。应付金额向上对齐显示精度后分配独占档位；创建订单、向上对齐、档位冲突递增和重选四条路径都守在上游商城能用 float64 验签的 `[0.0001, 1000000)` 之内，没有合法档位时直接拒绝选择付款方式，不截断、不调低金额，也不留下档位占用。
- 交易以 `(provider, event_id)` 唯一。到账证据与核销归属共用一张表，订单归属也有唯一约束。
- Binance Pay 交易历史以 `transactionId` 为事件身份；实测响应还带纯数字 `orderId`（用户在 App 账单里可复制的订单号），后台参考号默认记录 `orderId`。只有收款方向（实测收款记录 `amount` 为正、出账记录为负且明细为正幅度）的 `PAY` / `C2C` 且回填了收款 UID 的记录才可核销；总额与资产明细同时提供时必须全部可精确解析且一致，单资产明细而总额为 0 这类文档未定义的形态同样拒绝自动认领；多个资产明细保留为一个歧义事件，禁止自动认领。
- OKX 使用充值 `depId` 作为事件 ID、`fromWdId` 作为查询参考号，`ts` 是记录创建时间。只有 `state=2`（deposit successful）且回填 `fromWdId` 的站内转账才可核销，其余状态保留为待确认证据；缺少 `depId` 或分页边界无法推进时整次查询失败，不推进扫描进度。
- 交易所允许 8 位小数而支付域只有 6 位：超出精度的记录保留为证据但拒绝核销，原始精确金额与原因存入 `RawAmount` 供后台核对，不会让整次查询失败。响应契约不完整（缺少 `data`、`data` 非数组或 `data:null`）时整次查询失败，不推进扫描进度。
- 核销要求平台、收款账户、币种、完整金额、付款时间窗口全部匹配，且只有一个候选订单。自动扫描通过 `store.Process` 核对到账，是否可核销只看订单与金额档位是否仍处于占用状态，不看扫描器读到这笔流水的时间。
- 收银台不提供自助查单或手动提交流水入口；付款状态由后台自动扫描更新。
- 订单只有在成功扫描覆盖完整付款窗口（含宽限期）之后才会过期；交易所查询失败或扫描落后时订单保持待付款，仍可能按时付款的订单不会被永久关闭。窗口内出现唯一匹配订单的未确认到账时，持久化补查任务保留至该订单自己的有效期结束后 48 小时；超期转人工核对。
- 活跃付款与持久补查任务按平台间隔扫描；空闲时每分钟对账，取消后到账仍保留证据。增量扫描不跳过游标后的空白历史，未确认到账按原始时间专项补查。TON 每轮读取一页，证据与 LT/Hash 检查点原子提交，整个固定范围完成才推进时间游标；宕机、超时和大量历史不会强迫每次从钱包最新记录重新开始。
- 每种收款指令保存独立 `PaymentAttempt`，保留地址、金额和原付款窗口；切回旧方式复用原金额，重选不解除旧尝试的收款责任。第一笔唯一匹配到账核销订单，其他重复付款保留为额外到账证据。金额档位保留至独立结算期结束；主动取消停止自动认领。
- 已支付状态、资金归属及回调任务在同一数据库事务提交。仅发送 `status=2` 成功回调，不发送过期通知。
- 回调用递增尝试次数隔离过期执行者，保留有限重试及结果日志。仅 2xx 且正文 `success` / `ok` 为商户确认；交付幂等由商城实现。
- 后台只展示证据与状态，没有绕过交易唯一约束的强制支付入口。

`/healthz` 检查数据库连通；`/readyz` 还要求已配置的平台最近成功完成扫描且进度没有积压（没有待付款订单的空闲期不要求游标新鲜）。后台可查看未归属事件、扫描错误及未确认回调。对歧义或最终关闭后的到账，保留证据并交由人工在商城和交易所核对。

```sh
go test ./...

docker build -t litepay:dev .
```

小额真实收款的人工验收步骤见 `docs/acceptance-real-payment.md`；该清单目前只记录离线与只读已验证项，真实资金闭环尚未执行。

Dockerfile 以非 root 用户运行。自行挂载配置及可写数据目录。仓库提供 `scripts/payment_db.py` 用于一致性备份、完整性检查、恢复与离线演练；生产部署和回滚按 [支付运维](docs/operations.md) 操作。模拟测试通过不能替代真实交易所字段、只读权限、到账延迟及商城幂等交付的实际验收。

## 平台配置与关闭订单

设置页按币安、欧易、GRAM 分区，每个平台的收款 UID / 地址、API、开放币种和扫描间隔一起保存、核验。密钥留空保留原值；「清空本平台收款配置」只清除当前平台。旧版共享币种在加载时转换为各平台可用币种，之后独立保存。

后台订单列表和详情页可关闭待付款订单。关闭会停止认领该订单的到账，保留金额冷却期；已支付订单不能关闭。商户可签名调用 `POST /api/v1/order/cancel-transaction`，传 `trade_id` 或 `order_id`，同时传入时必须对应同一订单。

独角未实现向 BEpusdt 派发取消时，可在独角数据库所在服务器运行 `scripts/dujiao_cancel_sync.py`。它每 5 秒只读查询已取消且未支付的订单，按支付渠道现有凭据签名请求指定网关，并把重试状态写入独立 SQLite 文件。配置的网关和付款链接域名必须都匹配；不会修改独角数据库。失败退避重试，已支付冲突记录日志供人工核对；网关订单不存在时重试 3 次后记录为缺失，不将其标记为关闭。

```sh
python3 scripts/dujiao_cancel_sync.py --database /path/to/dujiao.db --state /path/to/cancel-sync.db --gateway https://pay.example.com
python3 -m unittest discover -s scripts -p 'test_*.py'
```

生产回调须配置 `server.notify_hosts` 精确主机白名单，并使用 HTTPS；回调耗尽可在后台订单详情核对商城状态、填写原因后重新通知，历史尝试和操作人均保留。详见 [支付运维](docs/operations.md)。

付款窗口关闭后仍有独立的 48 小时迟到首次可见结算期，成功查询不被当作平台数据已稳定的保证；此期限是保守策略，不代表平台 SLA。超过期限，管理员可在订单详情申请有审计的历史补扫，证据验证通过后再核对商城状态并补单；主动取消订单禁止补单。三个平台独立调度，平台内串行，过期任务另行运行。窗口结束后确认的到账先挂起商户通知，核对商城状态后释放；生产 Token 轮换默认暂停，须先验收商城历史密钥兼容能力。精确金额扩容、重选限制与操作流程见 [支付运维](docs/operations.md#金额容量和重选限制)。
