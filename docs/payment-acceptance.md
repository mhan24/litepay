## 不涉及资金的只读预检

操作人员在授权的验收机上执行（此处只提供步骤，没有执行远端命令）：

```
/app/litepay -config /app/config.yaml -preflight
```

仅从现有SQLite settings加载受控凭据，数据库以只读方式打开，不创建/迁移数据库或生成Token。不打印UID、密钥、流水或原始响应。对每个配置平台查询账户UID并校验，读取最近2分钟历史（GET）。输出account_and_history_ok及安全诊断，失败或未配置退出码1。空历史只证明读取权限，不证明真实转账会出现。无须开启交易/提现权限，推荐限制IP，只读权限不足时先核对账户产品能力。

预检是手工一次性诊断，不自动使用本机.env或生产凭据，不上传数据库/原始响应/密钥。真实账户的子账户、地区API域名、UID收款资格和共享限流预算仍需操作人员确认。

## 就绪和对账

- `/healthz`：数据库连接的存活检查；维护期间仍可用。
- `/readyz`：维护门关闭、当前进程notifier/reaper近期工作成功、至少一个平台启用，所有启用平台最近扫描成功且未过期、无当前扫描错误。历史缺口会阻止就绪。未配置交易所时503是预期；workers_started可单独证明维护门解除后本地worker运行。
- 后台展示扫描最近成功、连续失败、持久化进度/缺口；待对账、超过24小时未确认、未归属/核销拒绝、回调重试/耗尽及租约待恢复数量。
- 流水账本显示真实交易标识。后台补单必须填写当前通道未归属流水号，沿用ClaimAndPay全部校验并消费该真实唯一键。不可捏造流水；终结、取消、旧UID或金额不一致等不能强制补单。
- 交易所已收款（可核查证据）≠LitePay已PAID≠商户ACK≠商城已交付。最后一步始终到商城核实，后台明确标为未知。
- 已关闭订单后发现旧付款、切换后付旧UID、错币/错金额、重复转账、不可恢复缺口：保留未归属证据，人工协调商城是否已交付及退款/补偿，不能自动重开、重归单或重复发货。

## 最小真实付款步骤（须用户另行授权并亲自转账）

1. 使用隔离验收部署和测试商品，确认本轮CI成功，备份已有数据，确认实际CPU架构。配置只读Key和收款UID，运行预检；任何失败先停止，不能付款。
2. 确认 `/readyz` 为200，后台两个启用平台均最近扫描成功、无缺口/积压/对账告警。核对商城实际部署版本与合同，测试商品库存和幂等交付，明确status=3兼容边界。
3. Binance/OKX、USDT/USDC各建一张独立测试订单。金额为商城和平台允许的最小金额；LitePay默认最低基础金额0.01、步长0.01，首档理论为0.02。**这不是交易所保证的最低限额**；真实最小金额以页面锁定应付值和交易所限制为准，不足则提高测试商品价格，禁止自行猜测尾数。每次只付一张，确认后再继续。
4. 用户核对平台、币种、收款UID和完整应付金额，亲自发起站内转账（不走链上）。记录交易ID和付款时间，在受控环境核对API出现时间/ts偏差、币种、receiverInfo/fromWdId、金额及是否含fundsDetail。
5. 核对incoming_txs只有一条、LitePay为PAID、回调ACK、商城订单已支付且交付次数恰好1。核对商品实际收到，不能仅看LitePay绿灯。记录API延迟是否超过宽限假设。
6. 首笔完整成功后，在验收环境重发同一回调或重启worker，确认交付仍一次。没有额外授权不进行第二次资金转账；重复付款/错误金额场景优先使用本轮模拟测试，不为故障验收无谓损失资金。
7. 任一异常停止新建单/转账。创建配置的`LITEPAY_DEPLOY_GATE`文件可阻止业务HTTP并暂停后续worker轮询；在途请求可能仍结束，严格冻结时还须停容器。保留数据卷、WAL、镜像和日志；业务放行后禁止自动恢复旧数据库。先一致性快照再人工对账，已确认款项不能被回滚抹除。
