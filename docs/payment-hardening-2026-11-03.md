# 支付审计跟进（2026-11-03）

当前本地基线为 1b04af3，工作区已有未提交的观察账本、商户重试、扫描游标及回调租约修复。本轮保留这些修改并补齐验证，不将它们全部算作本轮新增实现。

## 本轮补齐

- 交易核销与已有观察记录的已归属状态在同一数据库事务提交。
- 观察账本写入或扫描游标保存失败时标记扫描失败，不报告成功；观察写入失败不推进游标，下一轮重扫。
- OKX 满页的最老时间等于窗口起点时继续检查边界；同毫秒拥塞无法推进时明确失败，不把部分结果当完整结果。
- 回归测试覆盖观察写入失败后重试、OKX 起点边界饱和，以及支付完成后并发分配金额与不同流水号的重复转账。
- 新增 GitHub Actions 配置，执行 vet、竞态测试及构建。尚未推送或触发远端运行，也未修改分支保护。

## 保留并验证的已有改动

- 观察原因按优先级保留，成功认领后从未归属列表排除；旧数据通过 incoming_txs 排除。
- 完全相同的商户建单重试保留 READY 订单、金额及有效期；真实参数变更仍按原协议重建。
- 分平台保存扫描进度，失败不推进；无待支付订单时低频扫描；积压按时间块追赶。
- 回调任务采用持久化租约，进程中断后可重新调度。商户仍须按订单号幂等处理重复通知，这不是外部副作用的 exactly-once 保证。
- 观察记录按 30 天保留期清理。

## 尚未闭环的生产验收

1. 扫描游标覆盖服务停机补扫，但不等于交易所所有延迟都已覆盖。当前最大回溯为 7 天，且订单、金额档位仍受宽限期约束。终结后的历史付款能留痕，不会自动重开订单或补发支付成功通知。需设计人工对账/补偿及与商户终态的协调流程。
2. OKX 使用时间戳分页。同毫秒记录挤满一页时无法证明已读全；当前报错并保留游标，需要对账或交易所提供可稳定分页的接口，不能自动跳过该边界。
3. 金额存储及交易所解析仍有 float64；现有十进制修约匹配不等于完成端到端定点金额迁移。该迁移需兼容历史订单、槽位唯一约束和回调签名。
4. scripts/deploy.sh 仍采用开发模式，未补齐失败自动回滚和 SQLite 恢复演练。不得据此宣称具备生产灾备能力；也未执行部署脚本。
5. 未使用真实交易所账户发起付款或访问服务器。Binance、OKX 各需验收：正常付款、同流水重复扫描、不同流水重复付款、付款后接口延迟、服务重启补扫、回调超时及重试。核对订单、incoming_txs、观察账本、金额占用和商户实际结果。

这些边界仍阻止将本轮本地测试通过解释为生产上线许可。
