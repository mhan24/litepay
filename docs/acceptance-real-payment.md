# 小额真实付款人工验收清单（Binance / OKX）

> [!WARNING]
> **当前状态**：未执行任何真实资金转移，真实资金闭环尚未验收。
> 本清单严格区分「离线与只读已验证」和「必须由用户真实转账后才能判断」两类结论。
> 清单本身不构成任何通过结论；第 4、5 节的所有判定项在实际执行前一律标记为**未验证**。

> [!NOTE]
> **金额口径规范**：创建订单限制原始金额在 `[0.0001, 1000000)` 区间内。选择付款方式时分配的应付金额（`PayUnits`）同样严格约束在同一区间（覆盖向上对齐、档位递增与重选三条路径）。若无合法档位可用，系统直接拒绝选择付款方式，不截断、不调低、不四舍五入，亦不残留档位占用。

## 2. 只有真实资金才能判断（当前全部标记为未验证）

- **流水可见延迟**：真实 Binance Pay / OKX 站内转账记录在网关只读查询中的可见延迟及实际字段形态。
- **中间状态流转**：真实 OKX 内部转账是否出现 `state=1`（已入账）→ `state=2`（成功）的中间态，以及网关待确认证据能否在补查中正确推进至已支付。
- **商城发货幂等**：商城真实实例（dujiao-next）对回调签名的验证、`status=2` 处理逻辑与**发货交付幂等性**（模拟商城仅证明算法一致，无法替代真实数据库事务与发货链路）。
- **平台最低转账限额**：交易所自身最小转账限额与配置的最小应付金额的匹配性（例如 USDT 站内转账可能拒绝低于 0.01 的金额）。
- **公网网络与 TLS**：生产真实 `notify_url` 的公网可达性、TLS 握手及超时行为。
- **支付窗口充裕度**：在包含真实网络延迟的情况下，配置的付款窗口（订单有效期 + 宽限期）是否充足。

## 3. 前置准备（不涉及真实资金）

1. **后台配置（/admin/settings）**：核对只读 API 凭据、Binance / OKX 收款 UID、开放币种、应付精度（默认 2 位）、最小应付金额、金额步长与最大调整次数。
2. **商户接入配置（/admin/integration）**：读取 BEpusdt 接入地址与 Token，填入商户网关配置；根据需求设定 `reselect`（重新选择）开关。
3. **测试金额建议**：验收金额建议 **≥ 1 USDT**（规避交易所最小提现/转账限额），并确保订单总额在 `[0.0001, 1000000)` 区间内。
4. **整额建议**：商城订单金额建议取 `10.00` 等整额，便于人工核对“商城原始金额 / 应付金额 / 实际到账”三者的对应关系。
5. **明确付款账户**：明确本次验收的**唯一付款方账户**（必须与商户收款 UID 不同，且为已实名认证可转账 USDT 的独立账户）。

## 4. Binance 最小验收步骤（由操作人自行决定是否发起小额转账）

| 步骤 | 操作动作 | 记录与判定标准 |
| :---: | --- | --- |
| 1 | 商城创建测试订单，走 LitePay 网关 | 记录商城订单号与下单金额 |
| 2 | 收银台选择 Binance + USDT | 页面进入“确认付款信息”，显示精确应付金额与收款 UID |
| 3 | 记录网关交易号及精确应付金额 | 在 `/admin/orders/{trade_no}` 核对「网关订单」与「应付」两项；含全部小数位，逐位比对无四舍五入 |
| 4 | 由操作人自行决定是否发起小额转账 | 在 Binance App 发起站内转账（Binance Pay → 收款 UID，金额逐位照抄收银台应付金额），记录转账流水号/纯数字订单号或 `transactionId` |
| 5 | 核对流水扫描与自动到账状态 | 等待后台自动扫描。期望：订单状态由 `READY` 变更为 `PAID`，`实际核销` 显示到账时间 |
| 6 | 验证订单仅核销一次 | 后台「已认领资金事件」恒为 1 条；等待数轮自动扫描后依然为 1 条，状态不发生反复 |
| 7 | 验证商户回调验签与确认 | 后台「商户通知」显示尝试次数与「商户确认于 …」；商城侧订单转为已支付。若多次尝试未成功，记录每次的 HTTP 状态码与错误详情 |
| 8 | 验证商城最终交付状态（防重复交付） | 商城订单更新为已完成/已发货，且**仅交付一次**；人工再次触发重发通知后，商城端不应发生二次发货 |

**通过标准**：第 3 步金额与第 4 步实际转账完全一致；第 5 步订单恰好一次进入 `PAID`；第 6、8 步无任何重复核销或重复交付；第 7 步商城端明确返回确认（HTTP 2xx 且响应体为 `success` 或 `ok`）。

| 步骤 | 操作动作 | 记录与判定标准 |
| :---: | --- | --- |
| 1 | 商城创建测试订单 | 记录商城订单号与下单金额（建议与 Binance 验收使用不同订单号） |
| 2 | 收银台选择 OKX + USDT | 页面显示精确应付金额与 OKX 收款 UID |
| 3 | 记录网关交易号及精确应付金额 | 同第 4 节第 3 步要求 |
| 4 | 由操作人自行决定是否发起小额转账 | 在 OKX 发起站内转账（OKX 内部转账 → 收款 UID），记录**付款方提现编号**（`fromWdId`）、转账时间与精确金额 |
| 5 | 核对流水扫描与到账状态 | 等待后台自动扫描。期望：订单变更为 `PAID`，「已认领资金事件」的事件编号为充值 `depId` |
| 6 | 验证唯一核销 | 同第 4 节第 6 步要求 |
| 7 | 验证回调验签与商户确认 | 同第 4 节第 7 步要求 |

**通过标准**：满足第 4 节所有要求；额外确认未完成状态不提前核销，且最终依然严格只核销一次。

## 6. 失败与终止处理原则

- **超时未核销**：若超过订单有效期及宽限期仍未自动核销，**切勿重复付款**；完整保留转账截图与交易编号，将 `provider / depId 或 transactionId / 金额 / 时间` 提供给管理员在交易所与商城端人工核对。
- **回调未确认**：若商户回调始终未获确认，记录 LitePay 后台尝试的 HTTP 状态码、错误信息及商城端日志；商户确认成功前，商城端不会触发商品发货。
- **金额不一致**：若实际转账金额与应付金额存在任何微小差异，网关机制严格禁止自动核销并保留流水证据；此类订单必须由人工介入在商城侧线下处理，严禁手工篡改金额再次提交。
- **单一凭证原则**：单一凭证仅限执行一次小额验收；验收结论仅针对对应账户、指定币种及该时间段有效。
