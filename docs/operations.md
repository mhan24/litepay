# 支付数据备份与恢复

数据库包括订单、到账归属、平台凭据、补查任务、TON 检查点、回调队列和重试审计。备份包含密钥，脚本创建的数据库与清单权限为 `0600`。备份目录应由服务管理员控制，并复制到另一台主机的加密存储；仅保留同盘副本不能防止整机损坏。备份不打印凭据或原始行。

## 一致性备份和检查

需要 Python 3（标准库 SQLite、fcntl，Linux/macOS）。服务运行时使用 SQLite backup API 获取一致快照，包括 WAL 中已经提交的数据，不直接复制 `.db` 文件。

```sh
python3 scripts/payment_db.py backup --database /path/to/litepay.db --output /secure/backup/litepay-20261110T120000Z.db
python3 scripts/payment_db.py check --database /secure/backup/litepay-20261110T120000Z.db
python3 scripts/payment_db.py drill --database /path/to/litepay.db
```

输出只有完整性检查、表计数、版本和备份 SHA256；同名备份不会被覆盖。备份生成同名 `.json` 清单，恢复时必须保留。检查包含 SQLite integrity/foreign-key、已支付订单的唯一资金证据与回调、金额档位归属、确认任务与 TON 检查点。离线演练比较恢复前后的全部 SQL 数据，覆盖凭据、游标和回调预算；演练不会运行服务或发送通知。

生产应至少每小时执行一次备份，每天同步异机副本，并在更新前执行一次即时备份与恢复演练。监控备份任务退出码和最新成功时间；每月做一次隔离启动演练。保留期限按商户业务要求设置，不能仅依赖部署前手工备份。

## 单实例与恢复

服务对规范化数据库路径的 `.lock` 文件持有进程级排他锁；同一数据库第二个 LitePay 实例会拒绝启动。恢复工具使用同一把锁。禁止删锁文件来绕过检查；旧版本没有这项保护，因此更换版本时必须先停止旧容器，确认没有旧进程运行。

恢复始终写入**全新的数据库路径**，不覆盖当前数据库，不复制旧 `.wal`/`.shm` 到恢复目录。

```sh
python3 scripts/payment_db.py restore --database /secure/backup/litepay-20261110T120000Z.db --output /secure/recovered/litepay.db
python3 scripts/payment_db.py check --database /secure/recovered/litepay.db
```

1. 停止接单并停止网关，保存当前数据库的一致快照和配置。记录故障期间的订单与平台到账，备份时间后产生的数据不能通过恢复旧快照找回。
2. 恢复到新目录，设置服务 UID/GID 的所有权和数据库 `0600`、目录 `0700` 权限。
3. 用本次发布二进制和恢复数据库，在隔离网络中启动：Docker 使用 `--network none`，仅检查容器内 `/healthz` 和后台页面。不得把生产数据副本接入真实交易所或商城，以免重复通知。
4. 核对已支付订单、归属证据、补查任务、TON 的 LT/Hash 范围、回调次数与重新入队记录。任务和游标应与恢复快照一致。回调中途宕机的任务在原租约结束后可继续，但商城仍须按原 `order_id` 幂等交付。
5. 人工核对备份时点后平台的真实到账及商城状态，补齐缺失证据；不能仅凭金额截图标记付款。完成核对后才切换主库并恢复唯一生产实例。

## 发布和回滚

数据库加法升级保留付款尝试、密钥版本、补单审计和历史补扫任务，并初始化持久重选计数与过期检查时间。支持的数据库版本以 `internal/store/store.go` 的 `Open` 为准，备份工具同步验证对应结构。迁移保留当前选择；已有确认任务能证明的历史选择按关联证据恢复。已经被覆盖且没有任何确认任务的选择无法安全还原，不依据孤立金额档位猜测地址、订单或付款窗口。升级前的二进制可能拒绝新数据库结构。发布前必须备份，不能修改版本号强行降级。

发布流程：通过 Go/脚本测试 → 构建目标架构静态二进制 → 记录二进制和源码 SHA256 → 在线一致性备份及离线恢复演练 → 用数据库副本在 `--network none` 容器验证升级 → 停止旧容器 → 更新配置、二进制和镜像 → 启动唯一实例 → 核对 `/healthz`、`/readyz`、数据完整性和回调白名单。

应用回滚只可使用支持当前数据库版本的已验证二进制；数据库故障走上面的恢复流程。不能在服务运行、已经产生新订单或新到账后用旧快照覆盖主库。更新期间暂停接单；保留旧镜像、配置、源码清单和数据库快照用于排查。

生产须显式配置 `server.production: true`（也是默认值），启动时拒绝 HTTP base_url 或空回调白名单；本机开发须显式设为 false。生产 `server.base_url` 使用 HTTPS；`server.notify_hosts` 必须列出实际商城的精确主机名，例如 `["shop.example.com"]`。创建订单和发送已有回调时都校验该策略，只允许 HTTPS 443，不使用通配符，不跟随重定向，原有公网拨号与 SSRF 防护继续生效。显式开发模式允许本地 HTTP 集成测试，改变 base_url 不会关闭生产策略。

## 超时确认和通知恢复

回调使用有上限的工作池，领取后连续处理队列，空队列退避；并发数由启动配置 `server.callback_workers` 控制，缺省 8，上限 32。每个订单保留原租约、尝试序号和签名版本，数据库串行提交归属，HTTP 请求并行执行。商城仍需按订单幂等交付。

后台概览展示通知积压、最老待确认通知等待秒数、历史补扫数与剩余时间窗口；已登录管理员也可读取 `<管理路径>/operations` JSON。剩余窗口长度不代表 API 请求次数，TON 还可能分页。Binance 指标仅估算当前客户端的 Pay 请求权重，其他应用或其他 API Key 对同一 UID 的调用不在此计数内；应为共享账户的其他用途预留额度。客户端已有串行间隔与 429 退避，历史补扫每步另有限制请求预算。

- 未确认到账有持久任务：唯一匹配订单保留至该订单实际 `expires_at + 48 小时`；不关联订单的证据保留至原到账时间后 48 小时。重复扫描和重启不会延长截止时间。超期转 `manual_review`，不再自动认领。
- TON 每轮只取一页，证据与 LT/Hash 检查点在同一事务落库。只有整个固定时间范围完成，时间游标才推进；中断后重读最后未提交页，依靠事件唯一键去重。
- 无活跃订单时账户仍每分钟对账，保留取消后新到账证据。已取消订单不能自动认领，也不会创建付款成功通知。
- 回调耗尽时在日志和后台概览显示告警。后台订单详情填写「核对商城状态后的重试原因」后重新通知，保留历史次数、日志和操作人；只允许已支付且有唯一资金证据的订单，发送中和已确认任务不能重新入队。
- 网关没有各商城通用的订单状态查询契约，因此恢复前的商城交付状态需要人工核对。重新通知使用原订单及事件标识；商城必须验签并幂等处理，不得再次交付相同订单。

## 付款重选、迟到首次可见和历史补扫

每个新的收款平台、币种与地址组合保存独立 PaymentAttempt；切回旧组合复用原金额、报价和付款窗口。旧、新付款方式均保留至原付款窗口结束，到账先匹配历史指令，再原子核销订单。第一笔到账唯一核销并将胜出方式用于回调；其他到账标记为 additional_payment，供人工核对退款，不再次交付。原金额档位不会因重选被提前复用。

不能把历史 API 成功返回空列表当作数据已稳定可见。系统保守保留原有效期后 48 小时的结算窗口；这一上限不是实测延迟承诺，仍需监测真实平台延迟。系统会持久化复扫整个原付款窗口（每轮分批），避免迟到首次可见记录落到增量游标之外；自然过期还要求完成在结算期限之后开始的最后一次完整窗口复扫。超过此界限的记录不能自动补单。后台可填写原因申请历史补扫，任务每轮分批推进、重启后继续，原始平台证据经过相同身份、金额和 TON 最终性检查后入库；不会直接重开已关闭订单。补扫旧地址时必须仍有匹配该收款账户的 API 配置，账户不一致的任务标记 blocked。

自然过期订单可在核对商城未交付且同意接受订单后，选择已确认资金事件并填写原因补单。仅允许原付款窗口内、唯一匹配已保存付款尝试的证据；拒绝已认领、歧义、未确认或主动取消订单。补单与资金认领、审计和通知任务在同一事务内完成。补扫和补单均需要管理员会话与 CSRF。

## 金额容量和重选限制

金额分配优先使用配置的步长；粗档位耗尽后，在相同金额上限内分配六位小数空档。付款人必须按收银台显示的全部小数位转账。历史档位仍保留至结算期限。默认 10 USDT 示例的范围仍为 10.00 至 10.99，共有 990,001 个微单位金额；这是有限的理论空间，邻近定价共享范围，不能当作吞吐量承诺。GRAM 尾差仍受报价容差约束。

重选限制持久化在订单内，重启不会清空；上限见 `internal/store/allocation.go` 的 `MaxPaymentAttempts`、`MaxSelectionChanges` 和 `SelectionInterval`。`internal/server/selection_limit.go` 对付款方式接口施加每 IP、每订单的分钟请求限制，返回 429 与 Retry-After。生产反向代理必须与 `server.trusted_proxies` 一致，不能信任任意客户端提供的地址头。

过期检查按 `next_expiry_check_at` 索引分批执行，未来结算截止时间的订单不逐张读取；缺少扫描覆盖的订单退避后再查，仍须满足完整窗口复扫与确认任务约束。参数见 `internal/store/expiry.go`。监控付款扫描进度、实际到账延迟和数据库等待；CI 的容量测试与内存库基准用于防止算法退化。

付款窗口结束后，页面显示「资金核对中」并停止提供新付款指令，最终关闭后显示「订单已关闭」。窗口结束后才确认的合法到账记录为 PAID，但回调进入 `merchant_review`，不会自动通知商城交付。管理员须先核对商城未取消且同意交付，再在订单详情填写原因释放通知；商城已取消的到账应线下处理退款。取消同步仍需持续运行，后台概览会提示待核对通知。

## 密钥版本与独立调度

生产默认禁止 Token 轮换。只有商城完成历史密钥兼容验收后，才能在启动配置中启用 `server.merchant_key_versions`；该开关不能从管理后台绕过。仅支持一个 auth_token 的商城须保持关闭。

订单创建时固定签名密钥版本，付款成功的回调任务保留该版本，重新通知也不隐式改用新 Key。Token 轮换后，旧 Token 不能创建新订单；历史回调仍用原版本。设置页和接入页展示未确认回调数量。商城须按订单保留对应旧密钥的验签能力；不能只替换全局单个 Token 后丢弃仍有历史订单引用的密钥。历史密钥与当前凭据一样保存在私有数据库与备份中，本版不自动删除仍有订单引用的密钥。

Binance、OKX、TON 各有独立调度循环和锁；单个平台超时不阻塞其他平台或每秒的过期处理。平台内部普通扫描和管理员历史补扫串行，保留原有限速预算。TON 检查点查询限定当前收款地址，保存新地址时在同一事务关闭旧地址的活跃检查点。

历史复核按付款尝试选定时间的小时桶分组，同组共用覆盖结果，跳过没有付款尝试的历史空档。结算期限后的最终复核优先于管理员补扫和常规复核；常规复核完成后间隔一段时间才重查，参数见 `SettlementRefresh`。最终过期仍要求结算期限之后创建、覆盖整个付款窗口的成功复核，不把旧覆盖当作最终确认。默认历史时间片扩大至一小时，Binance 密集响应耗尽有界请求预算时缩小时间片并持久化，不推进尚未完整查询的范围。旧的未完成自动全账户任务迁移为 superseded，已写入的证据和管理员任务保留。

## 商城取消同步的部署与监控

取消同步是独立服务，需要与商城数据库部署在能够只读访问同一数据源的环境。不能因网关容器正常就认定关单同步正常。systemd 示例见 `scripts/litepay-cancel-sync.service.example`；服务异常自动重启，watchdog 仅在成功读取商城数据并完成一轮处理后续期。持续读取失败或任务卡住会触发重启，仍须监控服务退出码和网关 `/readyz`。

SQLite 使用现有 `--database` 路径，脚本以只读模式打开。PostgreSQL 使用只读角色，安装 psycopg 3（`pip install 'psycopg[binary]>=3,<4'`），通过权限为 0600 的环境文件提供 DSN，再使用 `--database-url-env DUJIAO_DATABASE_URL`，不要把含凭据的 DSN 放在命令参数。适配器强制只读事务；PostgreSQL 部署仍须用其真实商城表结构做取消、失败重试及已支付冲突验收，本地 SQLite 验收不替代该步骤。

启动脚本时增加 `--report-health`：每轮记录本地最近尝试和成功时间，每隔约 15 秒向网关发送签名心跳，包含失败积压与已支付冲突数。网关拒绝无效签名和过时报告，旧报告不能刷新健康状态。确认首次心跳成功后，在网关启用 `server.cancel_sync_required: true`；同步不健康、失败积压或超过 45 秒无心跳时 `/readyz` 返回 503，后台概览显示异常。应让外部监控持续检查 `/readyz` 并接入现有告警渠道。

公开收银台和订单状态接口共用独立的内存请求限制，参数见 `internal/server/read_limit.go`。前端单次请求结束后再排下一次，失败和 429 退避，隐藏页面降低轮询频率；生产还应在可信反向代理上配置客户端请求限制。GRAM 二维码携带与钱包链接相同的地址和纳单位金额，付款人仍须核对钱包实际展示的完整金额。
