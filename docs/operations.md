# 支付数据备份与恢复

数据库包括订单、到账归属、平台凭据、补查任务、TON 检查点、回调队列和重试审计。备份包含密钥，脚本创建的数据库与清单权限为 `0600`。备份目录应由服务管理员控制，并复制到另一台主机的加密存储；仅保留同盘副本不能防止整机损坏。备份不打印凭据或原始行。

## 一致性备份和检查

需要 Python 3（标准库 SQLite、fcntl，Linux/macOS）。服务运行时使用 SQLite backup API 获取一致快照，包括 WAL 中已经提交的数据，不直接复制 `.db` 文件。

```sh
python3 scripts/payment_db.py backup --database /path/to/litepay.db --output /secure/backup/litepay-20261110T120000Z.db
python3 scripts/payment_db.py check --database /secure/backup/litepay-20261110T120000Z.db
python3 scripts/payment_db.py drill --database /path/to/litepay.db
```

输出只有完整性检查、表计数、版本和备份 SHA256；同名备份不会被覆盖。备份生成同名 `.json` 清单，恢复时必须保留。检查包含 SQLite integrity/foreign-key、已支付订单的唯一资金证据与回调、金额档位归属、确认任务与 TON 检查点。离线演练比较恢复前后的业务 SQL 数据，覆盖凭据、游标和回调预算；恢复标识会有意更新，演练不会运行服务或发送通知。

生产应至少每小时执行一次备份，每天同步异机副本，并在更新前执行一次即时备份与恢复演练。监控备份任务退出码和最新成功时间；每月做一次隔离启动演练。保留期限按商户业务要求设置，不能仅依赖部署前手工备份。

## 单实例与恢复

服务对规范化数据库路径的 `.lock` 文件持有进程级排他锁；同一数据库第二个 LitePay 实例会拒绝启动。恢复工具使用同一把锁。禁止删锁文件来绕过检查；旧版本没有这项保护，因此更换版本时必须先停止旧容器，确认没有旧进程运行。

恢复始终写入**全新的数据库路径**，不覆盖当前数据库，不复制旧 `.wal`/`.shm` 到恢复目录。

```sh
python3 scripts/payment_db.py restore --database /secure/backup/litepay-20261110T120000Z.db --output /secure/recovered/litepay.db
python3 scripts/payment_db.py check --database /secure/recovered/litepay.db
```

1. 停止接单并停止网关，保存当前数据库的一致快照和配置。记录故障期间的订单与平台到账，备份时间后产生的数据不能通过恢复旧快照找回。
2. 恢复到新目录，设置服务 UID/GID 的所有权和数据库 `0600`、目录 `0700` 权限。
3. 用本次发布二进制和恢复数据库，在隔离网络中启动：Docker 使用 `--network none`，仅检查容器内 `/healthz` 和后台页面。不得把生产数据副本接入真实交易所或商城，以免重复通知。
4. 核对已支付订单、归属证据、补查任务、TON 的 LT/Hash 范围、回调次数与重新入队记录。任务和游标应与恢复快照一致。商城仍须按原 `order_id` 幂等交付；独立取消日志必须按下面的恢复代际重新核对，不能沿用其旧成功状态。
5. 人工核对备份时点后平台的真实到账及商城状态，补齐缺失证据；不能仅凭金额截图标记付款。切换到恢复库并启动唯一实例后，保持 `server.cancel_sync_required: true`，让取消同步完成代际核对；接单、付款指令、自动扫描、自然过期与商户通知在核对完成前暂停。`/healthz` 仅表示进程可用，恢复放行须检查 `/readyz`。

## 发布和回滚

数据库加法升级保留付款尝试、密钥版本、补单审计和历史补扫任务，并初始化持久重选计数与过期检查时间。支持的数据库版本以 `internal/store/store.go` 的 `Open` 为准，备份工具同步验证对应结构。迁移保留当前选择；已有确认任务能证明的历史选择按关联证据恢复。已经被覆盖且没有任何确认任务的选择无法安全还原，不依据孤立金额档位猜测地址、订单或付款窗口。升级前的二进制可能拒绝新数据库结构。发布前必须备份，不能修改版本号强行降级。

发布流程：通过 Go/脚本测试 → 构建目标架构静态二进制 → 记录二进制和源码 SHA256 → 在线一致性备份及离线恢复演练 → 用数据库副本在 `--network none` 容器验证升级 → 停止旧容器 → 更新配置、二进制和镜像 → 启动唯一实例 → 核对 `/healthz`、`/readyz`、数据完整性和回调白名单。

镜像内置 `config.production.yaml`，保留 `production: true` 与 `cancel_sync_required: true`，并故意留空站点地址与回调白名单；未挂载配置的镜像应退出，不能进入开发模式运行。部署时只读挂载填写完成的生产配置，文件须允许容器 UID 10001 读取，实际路径使用 `/app/data/litepay.db`。开发用 `config.example.yaml` 必须显式选择。`scripts/test_container.sh` 对实际构建镜像验证默认拒绝启动、显式 HTTPS 配置正常启动、非 root 与隔离网络约束；CI 执行相同检查。

应用回滚只可使用支持当前数据库版本的已验证二进制；数据库故障走上面的恢复流程。不能在服务运行、已经产生新订单或新到账后用旧快照覆盖主库。更新期间暂停接单；保留旧镜像、配置、源码清单和数据库快照用于排查。

生产须显式配置 `server.production: true`（也是默认值），启动时拒绝 HTTP base_url 或空回调白名单；本机开发须显式设为 false。生产 `server.base_url` 使用 HTTPS；`server.notify_hosts` 必须列出实际商城的精确主机名，例如 `["shop.example.com"]`。创建订单和发送已有回调时都校验该策略，只允许 HTTPS 443，不使用通配符，不跟随重定向，原有公网拨号与 SSRF 防护继续生效。显式开发模式允许本地 HTTP 集成测试，改变 base_url 不会关闭生产策略。

## 平台扫描与新付款指令

平台已配置不等于可以接收新付款。每次进程启动或该平台账户、凭据、端点配置变化后，必须先核验收款账户身份并完成成功扫描；持久化的旧游标不能代替本进程的首次成功。最新扫描报错、成功时间过旧或历史覆盖落后时，该平台的新付款指令暂停。时限见 `internal/worker/readiness.go` 的 `ScanFreshness` 与 `ScanCoverageFreshness`；空闲账户仍按已有周期对账，未就绪账户继续尝试补齐覆盖。

创建订单只要求至少一个符合商户币种限制的平台可用；付款选择、已有付款页面和状态查询再检查具体平台。一个平台失败不会阻止选择其他健康平台；`/readyz` 在取消同步保护通过、数据库可访问且至少一个平台可接收新付款时返回 200；部分平台故障时包含 `degraded: true`。`/readyz/providers/binance`、`/readyz/providers/okx`、`/readyz/providers/ton` 分别返回平台扫描与报价状态，故障平台返回 503；未知平台返回 404。平台接口不代表商城取消保护已经通过，实际接单仍检查全局保护。后台运维接口同时报告各平台与实际生效的生产、取消同步开关；后台概览保留故障通道告警。新付款暂停不会停止到账记录、确认任务、历史补扫和已核销订单的通知。已经展示的指令无法撤回，付款人在暂停前已转出的资金继续按原付款尝试核对。

## 超时确认和通知恢复

回调使用有上限的工作池，领取后连续处理队列，空队列退避；并发数由启动配置 `server.callback_workers` 控制，缺省 8，上限 32。每个订单保留原租约、尝试序号和签名版本，数据库串行提交归属，HTTP 请求并行执行。商城仍需按订单幂等交付。

后台概览展示通知积压、最老待确认通知等待秒数、历史补扫数与剩余时间窗口；已登录管理员也可读取 `<管理路径>/operations` JSON。剩余窗口长度不代表 API 请求次数，TON 还可能分页。Binance 指标仅估算当前客户端的 Pay 请求权重，其他应用或其他 API Key 对同一 UID 的调用不在此计数内；应为共享账户的其他用途预留额度。客户端已有串行间隔与 429 退避，历史补扫每步另有限制请求预算。

- 未确认到账有持久任务：唯一匹配订单保留至该订单实际 `expires_at + 48 小时`；不关联订单的证据保留至原到账时间后 48 小时。重复扫描和重启不会延长截止时间。超期转 `manual_review`，不再自动认领。
- TON 每轮只取一页，证据与 LT/Hash 检查点在同一事务落库。只有整个固定时间范围完成，时间游标才推进；中断后重读最后未提交页，依靠事件唯一键去重。
- 无活跃订单时账户仍每分钟对账，保留取消后新到账证据。已取消订单不能自动认领，也不会创建付款成功通知。
- 回调耗尽时在日志和后台概览显示告警。后台订单详情填写「核对商城状态后的重试原因」后重新通知，保留历史次数、日志和操作人；只允许已支付且有唯一资金证据的订单，发送中和已确认任务不能重新入队。
- 网关没有各商城通用的订单状态查询契约，因此恢复前的商城交付状态需要人工核对。重新通知使用原订单及事件标识；商城必须验签并幂等处理，不得再次交付相同订单。

## 付款重选、迟到首次可见和历史补扫

每个新的收款平台、币种与地址组合保存独立 PaymentAttempt；切回旧组合复用原金额、报价和付款窗口。旧、新付款方式均保留至原付款窗口结束，到账先匹配历史指令，再原子核销订单。第一笔到账唯一核销并将胜出方式用于回调；其他到账标记为 additional_payment，供人工核对退款，不再次交付。原金额档位不会因重选被提前复用。

不能把历史 API 成功返回空列表当作数据已稳定可见。系统保守保留原有效期后 48 小时的结算窗口；这一上限不是实测延迟承诺，仍需监测真实平台延迟。系统会持久化复扫整个原付款窗口（每轮分批），避免迟到首次可见记录落到增量游标之外；自然过期还要求完成在结算期限之后开始的最后一次完整窗口复扫。超过此界限的记录不能自动补单。后台可填写原因申请历史补扫，任务每轮分批推进、重启后继续，原始平台证据经过相同身份、金额和 TON 最终性检查后入库；不会直接重开已关闭订单。补扫旧地址时必须仍有匹配该收款账户的 API 配置，账户不一致的任务标记 blocked。

自然过期订单可在核对商城未交付且同意接受订单后，选择已确认资金事件并填写原因补单。仅允许原付款窗口内、唯一匹配已保存付款尝试的证据；拒绝已认领、歧义、未确认或主动取消订单。补单与资金认领、审计和通知任务在同一事务内完成。补扫和补单均需要管理员会话与 CSRF。

## 金额容量和重选限制

金额分配优先使用配置的步长；粗档位耗尽后，在相同金额上限内分配六位小数空档。付款人必须按收银台显示的全部小数位转账。历史档位仍保留至结算期限。默认 10 USDT 示例的范围仍为 10.00 至 10.99，共有 990,001 个微单位金额；这是有限的理论空间，邻近定价共享范围，不能当作吞吐量承诺。GRAM 尾差仍受报价容差约束。

重选限制持久化在订单内，重启不会清空；上限见 `internal/store/allocation.go` 的 `MaxPaymentAttempts`、`MaxSelectionChanges` 和 `SelectionInterval`。`internal/server/selection_limit.go` 对付款方式接口施加每 IP、每订单的分钟请求限制，返回 429 与 Retry-After。生产反向代理必须与 `server.trusted_proxies` 一致，不能信任任意客户端提供的地址头。

过期检查按 `next_expiry_check_at` 索引分批执行，未来结算截止时间的订单不逐张读取；缺少扫描覆盖的订单退避后再查，仍须满足完整窗口复扫与确认任务约束。参数见 `internal/store/expiry.go`。监控付款扫描进度、实际到账延迟和数据库等待；CI 的容量测试与内存库基准用于防止算法退化。

付款窗口结束后，页面显示「资金核对中」并停止提供新付款指令，最终关闭后显示「订单已关闭」。窗口结束后才确认的合法到账记录为 PAID，但回调进入 `merchant_review`，不会自动通知商城交付。管理员须先核对商城未取消且同意交付，再在订单详情填写原因释放通知；商城已取消的到账应线下处理退款。取消同步仍需持续运行，后台概览会提示待核对通知。

## 密钥版本与独立调度

生产默认禁止 Token 轮换。只有商城完成历史密钥兼容验收后，才能在启动配置中启用 `server.merchant_key_versions`；该开关不能从管理后台绕过。仅支持一个 auth_token 的商城须保持关闭。

订单创建时固定签名密钥版本，付款成功的回调任务保留该版本，重新通知也不隐式改用新 Key。Token 轮换后，旧 Token 不能创建新订单；历史回调仍用原版本。设置页和接入页展示未确认回调数量。商城须按订单保留对应旧密钥的验签能力；不能只替换全局单个 Token 后丢弃仍有历史订单引用的密钥。历史密钥与当前凭据一样保存在私有数据库与备份中，本版不自动删除仍有订单引用的密钥。

Binance、OKX、TON 各有独立调度循环和锁；单个平台超时不阻塞其他平台或每秒的过期处理。平台内部普通扫描和管理员历史补扫串行，保留原有限速预算。TON 检查点查询限定当前收款地址，保存新地址时在同一事务关闭旧地址的活跃检查点。

历史复核按付款尝试选定时间的小时桶分组，同组共用覆盖结果，跳过没有付款尝试的历史空档。结算期限后的最终复核优先于管理员补扫和常规复核；常规复核完成后间隔一段时间才重查，参数见 `SettlementRefresh`。最终过期仍要求结算期限之后创建、覆盖整个付款窗口的成功复核，不把旧覆盖当作最终确认。默认历史时间片扩大至一小时，Binance 密集响应耗尽有界请求预算时缩小时间片并持久化，不推进尚未完整查询的范围。旧的未完成自动全账户任务迁移为 superseded，已写入的证据和管理员任务保留。

已完整查询的区间另外持久化到 `HistoryCoverage`，跨分组跳过重复区间。复用保留原始观测时间，完成新任务不会刷新旧证据；最终过期要求整段覆盖的最早观测时间也晚于订单结算期限。旧格式的完整复扫按其创建时间保守解释。可复用区间有独立保留期，并在过期任务中有界清理，参数见 `internal/store/expiry.go`；清理只会导致额外查询，不改变原始资金证据或已完成任务。

历史任务使用有界优先级调度。每个平台按 `[最终、最终、最终、人工、最终、最终、最终、日常]` 循环，预定队列为空时回退到当前最高优先级。轮次在数据库中持久化，重启不会重置。持续有最终任务进入时，人工队列每八次调度至少得到一次机会，日常队列也有保留机会；同类任务按最近调度时间轮转，包括分页或失败任务。这里保证的是调度次数，不是完成时长，接口故障和积压任务数仍会影响等待时间。

## 商城取消与真实转账的异步窗口

健康心跳和发现探测只能证明此前一次同步的结果，不能把商城取消与真实转账放进同一事务。用户在取消尚未同步前仍可能使用旧指令转账，网关也可能已核销或开始发送通知；提高轮询频率不能消除这个窗口。商城必须在支付处理事务中复核取消状态，并拒绝为已取消订单自动履约。当前集成继续使用独立同步脚本，尚未部署 Dujiao Next 事务内取消事件或可靠事件队列；后续主动事件仍应保留轮询兜底，不能承诺撤回已转出的资金。

网关已经收到取消时，会拒绝新付款认领。若在原有效付款窗口内发现可唯一归属的已确认资金，保留未认领证据和原付款尝试，建立取消到账核对记录；若网关已经 PAID，则保留原核销历史，为该资金建立核对记录并暂停该订单的后续通知。新记录不会把已支付订单改为取消，也不会再次认领同一资金。无法唯一归属或不在原付款窗口内的资金仍保留为未匹配证据，不能仅凭金额强行归属。

管理员从后台概览进入待核对订单，核对原始资金事件、实际金额与币种、商城取消和交付记录，在原始平台流水中核实付款方账户，再在收款平台完成实际退款；不能仅凭聊天截图或手填地址决定退款目的账户。确认后填写退款凭证编号和核对说明，登记操作人、时间与恢复代际；此操作只记账，不发起转账。取消后到账的通知不会因退款登记而重新发送；发送中的通知必须先结束，再核对实际交付，才能登记退款。买家页面显示核对中或退款凭证已登记，实际到账仍需在原付款账户确认。

若同步日志有 `paid_conflict`，实际退款登记后，在商城服务器执行 `--review-conflict <网关订单号> --reason '<已核实的处理结果>'`，配合现有 `--database`、`--state`、`--gateway` 参数。命令重新检查商城取消身份，并要求网关存在当前恢复代际的完整退款审计，才把该项标为 `reviewed_conflict`；保留独立操作审计，随后由正常心跳重新核对健康。旧版冲突尚未在网关建立记录时，首次执行会向网关确认冲突并建立待核对记录，缺少退款审计仍返回失败；到订单详情完成实际退款登记后再执行。不要直接清空日志来恢复健康。

数据库恢复后，已有退款登记仍保留，但需要在新代际重新核对凭证；界面和脚本会要求复核，不能据此重复转出退款。原有资金认领、退款审计和回调幂等标识均保留。

## 商城取消同步的部署与监控

取消同步是独立服务，需要与商城数据库部署在能够只读访问同一数据源的环境。不能因网关容器正常就认定关单同步正常。systemd 示例见 `scripts/litepay-cancel-sync.service.example`；服务异常自动重启，watchdog 仅在成功读取商城数据并完成一轮处理后续期。持续读取失败或任务卡住会触发重启，仍须监控服务退出码和网关 `/readyz`。

SQLite 使用现有 `--database` 路径，脚本以只读模式打开。PostgreSQL 使用只读角色，安装 psycopg 3（`pip install 'psycopg[binary]>=3,<4'`），通过权限为 0600 的环境文件提供 DSN，再使用 `--database-url-env DUJIAO_DATABASE_URL`，不要把含凭据的 DSN 放在命令参数。适配器强制只读事务；PostgreSQL 部署仍须用其真实商城表结构做取消、失败重试及已支付冲突验收，本地 SQLite 验收不替代该步骤。

取消发现游标、待展开的商城订单、发送队列与重试次数都保存在独立日志库。每轮按取消时间和订单 ID 读取有限批次，将待展开任务与游标在同一事务提交；每张商城订单的付款记录也分页保存进度。发送队列独立领取到期任务，发送前重新查询商城状态、标识与当前凭据；关闭成功的历史日志不再参与每轮发送查询。首次升级旧日志库保留原去重记录，并从头分批建立发现进度。

慢速巡检按支付记录主键循环，每轮只读一个批次，用来发现倒填取消时间、付款元数据迟到和恢复后游标后方的记录；不要求商城修改 `updated_at`。默认批次与巡检间隔见 `scripts/dujiao_cancel_sync.py` 的 `AUDIT_PAYMENT_BATCH`、`AUDIT_INTERVAL`，历史回填发现延迟随整库大小增加，不能当作实时事件通知。`--rescan-history` 可主动重置发现进度，保留去重结果与重试任务，仍按批次处理。源支付最大 ID 回退会自动重建发现进度；最大 ID 未回退的恢复由循环巡检兜底。

每轮在本次增量发现游标之后额外读取至多一条记录，使用相同时间戳加订单 ID、以及更晚时间戳两次索引探测。即使已读批次没有本网关付款、本地发送队列为空，只要源库还有未读记录就不能上报完整或健康。探测结果随发现游标持久化；新日志尚未探测也按未完成处理。签名心跳和后台运维接口包含 `discovery_pending`（0/1 标记，不是剩余订单数）及 `discovery_lag_seconds`（已知最早未读取消记录距今秒数；无已知时间时为 0）。这只说明增量游标之后的记录；倒填时间或旧记录变更仍依赖上述循环巡检，不能把探测追平当作全库从未变更的证明。

升级包含发现指标的版本时，先更新取消同步脚本，再更新网关。数据库加法升级保留恢复代际、资金归属与任务，但使旧心跳失效，等待带发现指标的新签名报告；缺少这些指标的旧脚本不能重新放行。网关启动后还需等待各平台本进程首次成功扫描。

源库需要订单 `canceled_at` 索引、付款 `order_id` 索引与主键索引，标准 SQLite 商城迁移已包含；脚本本身不会修改商城表。PostgreSQL 大量相同取消时间的环境应由商城管理员建立 `(canceled_at,id)` 与 `(order_id,id)` 复合索引并检查执行计划。备份独立日志库时也使用 SQLite backup API（包括其所有表），不要只复制去重结果；恢复后保留发现表与未完成队列，不能手填最后 ID 跳过未发现区间。缺失或过旧的日志备份可从源库分批重建，可能重发取消请求，由网关幂等接口保护。停机期间正常取消通过持久时间游标补上，旧时间回填通过巡检补上。

启动脚本时增加 `--report-health`：每轮记录本地最近尝试和成功时间，每轮向网关发送签名心跳，包含失败积压与已支付冲突数。网关拒绝无效签名和过时报告，旧报告不能刷新健康状态。Dujiao Next 生产集成必须保持 `server.cancel_sync_required: true`，生产模板也默认开启；独立部署明确不依赖商城取消同步时才可自行关闭，生效值通过已登录后台的运维接口核对。恢复代际确认与当前同步健康分别检查。同步不健康、存在待处理或失败任务、已支付冲突、核对未完成，或超过 45 秒无心跳时，`/readyz` 返回 503，后台概览显示异常；网关自身暂停新建订单、付款指令和自动商户通知，不依赖反向代理摘除流量。恢复代际已经完成时，到账扫描、真实资金归属与证据入库继续运行，已排队回调保留原幂等标识和重试预算；新鲜心跳确认同代际核对完成且无积压、失败或冲突后才重新放行。已开始的 HTTP 通知无法撤回，商城仍须按订单幂等处理。应让外部监控持续检查 `/readyz` 并接入现有告警渠道。

`paid_conflict` 表示商城已取消而网关已确认到账，需要核对真实资金、商城取消和交付记录。冲突会持久保留，脚本上报不健康；即使发送方错误声明健康，网关也按冲突计数拒绝放行。重启或等待不会消除冲突，后台即使未启用必需心跳也显示告警。退款登记及 `--review-conflict` 核对流程见上面的取消到账流程。不得为恢复接单直接清空日志或把已支付订单强制改为取消；人工完成商户交付或退款核对后，应保留处理凭据并核对两侧状态。

签名心跳包含 `missing` 计数。连续三次 `record not found` 的任务保留为 `missing_gateway`，计入失败与就绪检查异常；它既不是关闭成功，也不会因时间过去自动解除。当前网关对同时带有效网关、商户订单号的取消请求持久化取消意图：若订单暂未创建，确认保存意图后才返回成功，并阻止该商户订单晚到创建。已有订单必须与两个标识一致，已支付订单仍拒绝取消；自然过期订单被商户明确取消后转为 CANCELED，不能再人工补单。旧网关仍可能返回 `missing_gateway`，必须单独核对。

确需人工接受旧网关的缺失异常时，管理员使用 `--review-missing <网关订单号> --reason '<已核实的事实和处理结果>'`。脚本重新核验商户取消状态与两个标识，再请求网关确认，记录操作系统用户、原因、时间与代际；不会直接修改网关资金归属。审核只对当前代际有效，下次恢复仍须重新核对。不要批量忽略未知异常。`--once` 只有在待处理任务清空、无失败和冲突、所要求的健康上报成功且恢复核对完成时才返回 0；超时、缺失异常、未完成批次或上报失败返回非零。

## 网关恢复与独立取消日志

数据库保存独立的恢复标识。普通进程重启保留标识；`payment_db.py restore` 在支持代际的数据库副本中生成新标识并取消放行，旧版快照首次由新服务打开时也生成新标识。手工复制数据库等绕开恢复工具的操作，必须首次启动时显式添加 `-recover-reason '<恢复来源与核对原因>'`，随后移除此一次性参数；不能假定直接替换同代际文件会被自动检测。不要把这个参数永久写入服务启动命令。

取消同步每轮取得带签名的恢复标识，变化时从源商城支付记录按主键分批复核。历史 `closed` 和曾人工审核的记录都须重新通过幂等取消接口确认；成功凭据按代际分别保存，不覆盖旧审计。源库扫描完成、发送与发现队列清空且无未解决异常后，同步才请求放行当前代际。旧代际心跳不能解除恢复暂停。启用这项保护需要网关与脚本一同升级，并配置 `server.cancel_sync_required: true`。回调与新接单恢复前仍须由运维核对快照之后真实资金、商城交付记录与待通知任务；取消重放不能替代资金对账。

公开收银台和订单状态接口共用独立的内存请求限制，参数见 `internal/server/read_limit.go`。前端单次请求结束后再排下一次，失败和 429 退避，隐藏页面降低轮询频率；生产还应在可信反向代理上配置客户端请求限制。GRAM 二维码携带与钱包链接相同的地址和纳单位金额，付款人仍须核对钱包实际展示的完整金额。

## TON 数据提供商信任边界

TON/GRAM 收款以 Toncenter v2 的交易 BOC、账户、哈希、LT 与执行结果为基础，交叉检查其 v3 交易主链索引和主链高度。字段定义见 [Toncenter v3 交易接口](https://docs.ton.org/ecosystem/api/toncenter/v3/blockchain-data/get-transactions)，主链确认要求见 [TON 支付文档](https://docs.ton.org/applications/payments/overview)。两路数据仍来自同一服务商，当前实现信任其规范链索引，不提供独立验证者证明，也没有第二个独立节点交叉验证。BOC 与索引一致不应表述为已自行验证整条主链。

本项目的 GRAM 指 TON 网络原生资产；行情适配器读取 Kraken 的 `TONUSD` 交易对字段，同名 Jetton 不属于本项目的原生币收款流程。资产展示名称与行情字段名称分别维护，不能仅按名称差异判定资产不一致。
