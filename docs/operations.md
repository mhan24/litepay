# 支付数据备份与恢复

LitePay 的 SQLite 数据库包含订单、资金归属证据、平台 API 凭据、补查任务、TON 检查点、商户回调队列及重试审计日志。备份文件内包含敏感密钥，脚本创建的备份数据库与元数据清单权限严格设定为 `0600`。

> [!IMPORTANT]
> **安全与备份规范**：
> - 备份目录应由服务管理员严格控制，并定期同步至独立异机加密存储；仅在同一物理磁盘保留副本无法防御整机故障。
> - 备份脚本执行过程中绝不向控制台打印 API 凭据或明细行数据。

---

## 一致性备份和检查

### 环境与执行命令

备份脚本运行依赖 Python 3（标准库 `sqlite3` 与 `fcntl`，支持 Linux / macOS）。在服务正常运行期间，系统使用 SQLite 原生 Backup API 获取一致性快照（完整包含 WAL 日志中已提交的数据），严禁直接在文件系统层面复制 `.db` 文件。

```sh
# 执行一致性热备份
python3 scripts/payment_db.py backup --database /path/to/litepay.db --output /secure/backup/litepay-20261110T120000Z.db

# 检查备份完整性
python3 scripts/payment_db.py check --database /secure/backup/litepay-20261110T120000Z.db

# 离线演练恢复与比对
python3 scripts/payment_db.py drill --database /path/to/litepay.db
```

### 检查机制与演练策略

- **清单与防覆盖**：备份输出仅包含完整性校验结果、数据表计数、数据库版本及备份文件的 SHA256；同名备份不会被静默覆盖。备份会自动生成同名 `.json` 元数据清单，执行数据恢复时必须与数据库文件一同保留。
- **校验内容**：检查流程包括 SQLite `integrity_check`、外键约束校验、已支付订单与资金证据的唯一性约束、金额档位归属状态、确认任务及 TON 检查点完整性。
- **离线演练**：演练工具在内存中比对恢复前后的业务 SQL 数据（覆盖平台凭据、扫描游标与回调配额）；演练过程中会主动更新恢复代际标识，但绝不启动服务进程或向商户发送回调。
- **运维调度建议**：生产环境建议至少每小时执行一次自动热备，每天向异机加密存储同步，并在版本更新前执行即时备份与恢复演练。管理员应持续监控备份任务的退出码与最新成功时间戳，每月执行一次隔离环境冷启动验证。

## 单实例与恢复

### 排他锁保护

LitePay 对规范化后的数据库路径持有专属 `.lock` 进程级排他锁；若存在其他运行中的进程，第二个 LitePay 实例将直接拒绝启动。恢复工具亦使用同一把文件锁。

> [!CAUTION]
> 严禁通过手工删除 `.lock` 文件绕过互斥检查！更换服务版本或部署新容器时，必须先完全停止旧容器，确认无残留进程占用后再启动新实例。

### 恢复操作步骤

数据恢复必须始终写入**全新的数据库路径**，严禁直接覆盖正在使用的数据库，亦不要将旧的 `.wal` / `.shm` 文件复制到恢复目录。

```sh
# 恢复至新路径
python3 scripts/payment_db.py restore --database /secure/backup/litepay-20261110T120000Z.db --output /secure/recovered/litepay.db

# 检查恢复库的数据完整性
python3 scripts/payment_db.py check --database /secure/recovered/litepay.db
```

1. **停机与保护**：停止商户接单并停止网关进程，保留当前数据库的一致性快照及配置文件。人工记录停机期间产生的订单与平台到账（快照时间点后产生的数据无法通过旧快照找回）。
2. **重置权限**：将备份恢复至全新目录，修正文件所有权（归属服务运行 UID/GID），设置数据库文件权限为 `0600`、目录权限为 `0700`。
3. **网络隔离验证**：使用当前版本二进制与恢复后的数据库，在网络隔离环境中启动验证（如 Docker 使用 `--network none`），仅访问容器内部的 `/healthz` 探针及后台页面。**严禁将生产数据副本直接连接至真实交易所或商户端**，避免产生重复通知。
4. **状态核对**：登录后台核对已支付订单、资金证据归属、补查任务、TON 检查点（LT/Hash 范围）、回调尝试次数与重新入队记录。各项任务状态与游标必须与恢复快照一致。商户端必须基于原始 `order_id` 实施幂等发货；独立的取消同步日志必须按全新的恢复代际重新核对。
5. **代际确认与放行**：人工核对备份时点之后交易所/链上的真实到账及商户交付状态，补齐遗漏流水证据（严禁仅凭转账截图标记付款）。将主服务切换至恢复库并启动唯一实例，保持 `server.cancel_sync_required: true`，待取消同步服务完成代际核对后方全面恢复业务。在代际核对完成前，新接单、付款选择、自动扫描与商户通知保持暂停。

## 发布和回滚

### 升级与迁移机制

- **加法升级规则**：系统数据库支持的加法升级范围以 `internal/store/store.go` 中的 `Open` 为准，备份工具同步校验相应结构。迁移过程完整保留历史付款尝试、密钥版本、人工补单审计记录与历史补扫任务。
- **选择状态恢复**：迁移保留当前选定的付款方式；存在确认任务的历史选择按关联证据恢复；已覆盖且无任何确认任务的孤立历史选择不强行猜测地址与窗口。
- **版本约束**：旧版二进制可能拒绝新数据库结构。升级发布前必须执行一致性备份，严禁擅自修改版本号强制降级。

### 标准发布流程

```
运行全量单元测试与脚本测试
            ↓
构建目标架构静态二进制并记录 SHA256
            ↓
执行在线一致性热备与离线演练恢复
            ↓
在隔离网络容器 (--network none) 验证数据库加法迁移
            ↓
停止旧容器并更新配置与二进制
            ↓
启动唯一生产实例并校验探针 (/healthz, /readyz) 与白名单
```

### 容器安全与生产配置

- **容器权限与路径**：官方镜像内置 `config.production.yaml`（默认 `production: true` 且 `cancel_sync_required: true`，故意留空站点域名与回调白名单）。未挂载有效生产配置的镜像将拒绝启动。
- **挂载规范**：将填写完毕的生产配置以只读方式挂载至 `/app/config.yaml`（允许容器 UID 10001 读取），持久化数据目录挂载至 `/app/data`，实际数据库路径使用 `/app/data/litepay.db`。`config.example.yaml` 仅限本地开发测试使用。
- **安全约束**：生产模式强制要求 `server.base_url` 采用 HTTPS 协议，且 `server.notify_hosts` 必须列出商户主机的精确域名（如 `["shop.example.com"]`）。系统在创建订单及发送回调时均严格执行此策略，只允许 HTTPS 443 端口，不支持通配符，不跟随 30x 重定向，SSRF 与公网防护策略持续生效。
- **版本回滚**：应用回滚仅可使用兼容当前数据库结构的已验证二进制。若遭遇数据库损坏，必须走上述标准恢复流程，严禁在服务运行中直接用旧快照覆盖主库。

## 平台扫描与新付款指令

### 平台就绪判定条件

平台配置完成并不代表立即可接收新付款。在进程每次启动、或该平台的账户/凭据/接口端点发生变更后，系统必须重新核验收款账户身份并完成首次成功扫描；数据库中持久化的旧游标不能替代当前进程的首次成功。

- **暂停接单情形**：若最新扫描报错、最后成功扫描时间过旧、或历史覆盖落后过多，该平台的新付款指令将自动暂停。具体判定时限详见 `internal/worker/readiness.go` 中的 `ScanFreshness` 与 `ScanCoverageFreshness`。
- **全局与部分降级**：
  - 创建订单仅要求至少有一个满足商户币种约束的平台处于就绪状态；收银台选择付款方式时再核验具体平台。
  - 单一平台故障不影响其他健康平台的服务；`/readyz` 在取消同步保护通过、数据库正常且至少一个收款平台就绪时返回 200（若存在部分平台故障，返回体包含 `degraded: true`）。
  - 各平台细分探针 `/readyz/providers/binance`、`/readyz/providers/okx`、`/readyz/providers/ton` 分别反馈平台扫描与实时报价状态，故障平台返回 503。
- **既有流水保障**：新付款指令暂停不会阻断已产生流水的入库、确认任务推进、历史补扫及已核销订单的商户回调。收银台此前已向买家展示的指令不可撤回，买家在暂停前已转出的资金仍按原付款尝试正常匹配与核销。

## 超时确认和通知恢复

### 回调队列与并发控制

- **工作池控制**：商户回调采用有上限的并发工作池处理，并发数由 `server.callback_workers` 控制（默认 8，最大 32）。每个订单保留独立的数据库租约、尝试序号及签名密钥版本；资金归属在数据库内串行提交，HTTP 回调请求在工作池内并行执行。
- **商户端契约**：商户端接收到通知后必须基于订单号实施幂等交付，并返回 HTTP 2xx 且响应体为 `success` 或 `ok`。
- **运维指标**：后台管理概览展示待发通知积压、最老待确认通知等待时间、历史补扫任务及剩余时间窗口。

### 补查任务与重试策略

- **持久化到账补查**：未确认到账设立持久补查任务；唯一匹配候选订单的记录保留至订单 `expires_at + 48 小时`，未关联订单的证据保留至原到账时间后 48 小时。超期后转入 `manual_review` 状态，停止自动认领。
- **TON 原子检查点**：TON 扫描每轮仅拉取一页，交易证据与 LT/Hash 检查点在同一事务提交，完整时间范围全部核对完成才推进时间游标。
- **空闲周期对账**：无待付款订单的空闲期，后台每分钟对账一次，订单取消后到账的流水仍会被完整记录为证据（但已取消订单不会被自动认领，亦不发送成功回调）。
- **回调重试耗尽处理**：若回调重试次数耗尽，后台订单详情支持在核对商城发货状态并填写原因后手动重新通知，系统完整记录历史尝试、操作人及重发原因。

## 付款重选、迟到首次可见和历史补扫

### 付款重选机制

每个新的收款平台、币种与地址组合均生成独立的 `PaymentAttempt` 记录；若买家切回旧组合，系统复用原金额、报价与付款窗口。

- **多指令并行保护**：新旧付款方式的收款责任均保留至原付款窗口结束。到账流水先匹配历史指令，再原子核销订单。
- **多笔到账处理**：第一笔唯一匹配流水核销订单并将对应方式用于回调；后续到达的重复付款标记为 `additional_payment`，仅供人工核对退款，绝不触发二次发货。原金额档位不会因重选而被提前释放。

### 48 小时迟到结算期

接口返回空列表不能视作平台数据已绝对稳定。系统在订单有效期结束后，保留独立的 48 小时迟到首次可见结算期（此期限为防御性设计，不代表交易所 SLA）。

- **结算期复扫**：系统分批持久化复扫整个原付款窗口，防止迟到流水落入增量游标之外；订单自然过期要求完成在结算期之后发起的最后一次完整窗口复扫。
- **历史补扫任务**：超出结算期限后，管理员可在后台订单详情页申请历史补扫任务。补扫流水经严格身份、金额与 TON 最终性验证后方可入库，但不会直接重开已关闭的订单。
- **补单核销流程**：自然过期的订单经核对商户未发货且同意接收后，管理员可关联已确认的资金事件填写原因执行人工补单。系统严禁为歧义、未确认或主动取消的订单补单。

## 金额容量和重选限制

### 金额档位分配

- **档位计算**：金额分配优先使用配置的基础步长；粗档位用尽后，系统在相同金额上限内细分至 6 位小数空档。付款人必须按照收银台显示的全部小数位完整转账。
- **容量理论上限**：以默认 10 USDT 订单为例，可选区间为 10.00 至 10.99，理论包含 990,001 个微单位金额。这是共享的有限空间，不可视作真实并发吞吐承诺。GRAM 换算尾差受实时报价容差严格约束。

### 频率与防刷限制

- **重选限制**：订单重选次数持久化在订单记录中，重启不会重置（参数见 `internal/store/allocation.go` 中的 `MaxPaymentAttempts`、`MaxSelectionChanges` 与 `SelectionInterval`）。
- **接口限流**：收银台付款方式切换接口对单个 IP、单个订单实施分钟级限流保护，超限返回 HTTP 429 与 `Retry-After`。反向代理配置必须与 `server.trusted_proxies` 严格对应。
- **分批过期扫描**：过期检查基于 `next_expiry_check_at` 索引分批执行，未到结算截止期的订单不逐笔扫描。参数见 `internal/store/expiry.go`。

## 密钥版本与独立调度

### API Token 轮换策略

- **生产开关防护**：生产环境默认禁止 Token 轮换。只有当商户端完成对历史密钥兼容性的联动验收后，方可在启动配置中开启 `server.merchant_key_versions: true`；该开关严禁从管理后台直接绕过。
- **密钥版本固化**：订单创建时固化当前签名的密钥版本，回调任务与重发通知严格沿用该版本。Token 轮换后，旧 Token 不再接受新订单创建，历史回调仍使用原版本验签。商城端必须具备多版本密钥验签能力。

### 平台独立调度与优先级

Binance、OKX 与 TON 拥有完全独立的调度循环与互斥锁；单个平台超时不阻断其他平台运行。

- **平台内串行**：平台内部常规扫描与管理员历史补扫串行推进，保护 API 调用配额。
- **优先级队列**：历史任务采用有界优先级轮转调度，每个平台按照 `[最终、最终、最终、人工、最终、最终、最终、日常]` 循环执行。当最终复核任务持续产生时，人工补扫任务每 8 次调度至少保证获得 1 次执行机会。

## 商城取消与真实转账的异步窗口

### 异步冲突说明

商城订单取消与链上/平台转账分属不同系统，无法纳入同一个数据库事务。即使提高轮询频率，依然存在买家在取消尚未同步到网关前完成转账、或网关刚好核销并发出回调的边界窗口。

- **商户端防护**：商城端在处理发货事务时，必须再次复核订单自身的取消状态，拒绝为已取消订单自动发货。
- **网关防误领**：网关一旦同步到取消状态，立即停止新到账的自动认领；若订单已处于 `PAID` 状态，系统保留原核销记录，暂停该订单后续商户通知，并为每笔已确认的资金流水生成「取消后到账核对」待办任务。

### 退款审计与冲突核对流程

1. **线下退款**：管理员在后台概览查看待核对订单，核对原始流水、金额、币种与商城发货记录；在平台流水中严格核实付款方原账户，通过交易所或链上向原账户转账退款（严禁仅凭买家聊天截图退款）。
2. **凭证登记**：完成实际转账后，在订单详情页填写退款凭证编号与核对说明。此操作仅做审计记账，网关不发起实际资金转账。
3. **消除冲突（paid_conflict）**：若同步脚本日志中出现 `paid_conflict`，在登记退款凭证后，前往商城数据库所在服务器执行：
   ```sh
   python3 scripts/dujiao_cancel_sync.py --database /path/to/dujiao.db --state /path/to/cancel-sync.db --gateway https://pay.example.com --review-conflict <网关订单号> --reason '<已核实的处理结果>'
   ```
   脚本将重新校验商户取消状态及网关的退款审计记录，通过后将该项标为 `reviewed_conflict`。严禁通过直接删除日志文件来消除告警。

## 商城取消同步的部署与监控

### 部署架构

取消同步脚本是独立的守护进程，必须部署在能够只读访问商城数据库的环境中。Systemd 服务示例详见 `scripts/litepay-cancel-sync.service.example`。

- **数据库模式**：
  - **SQLite**：使用 `--database` 路径，脚本以只读方式打开。
  - **PostgreSQL**：使用只读角色，安装 `psycopg 3`，通过权限为 `0600` 的环境变量文件注入 DSN（使用 `--database-url-env DUJIAO_DATABASE_URL`），严禁在命令行明文传递凭据。
- **日志库隔离**：取消发现游标、待处理订单与重试队列均保存在独立的 SQLite 日志库中。

### 巡检与健康心跳

- **双向心跳**：启动脚本时添加 `--report-health` 参数，每轮向网关发送带签名的健康心跳（包含失败积压与已支付冲突计数）。若超过 45 秒无心跳，网关 `/readyz` 返回 503，后台显示告警，并自动暂停新接单与商户通知。
- **循环巡检**：脚本包含慢速循环巡检机制，分批检测倒填取消时间或恢复后的旧记录，防止漏单。
- **缺失订单处理**：若任务连续 3 次返回 `record not found`，记录为 `missing_gateway`。管理员可通过 `--review-missing <网关订单号> --reason '<说明>'` 完成人工复核。

## 网关恢复与独立取消日志

数据库包含独立的恢复代际标识。通过 `payment_db.py restore` 恢复的数据库会自动生成新代际标识并暂停对外放行。

- **冷复制提示**：若运维通过手工复制数据库等方式恢复，必须在首次启动时显式附加一次性参数 `-recover-reason '<恢复来源与核对说明>'`，随后移除该参数。
- **代际重放**：取消同步脚本检测到恢复代际变更后，会从源数据库按主键分批重新复核所有取消记录，确认无未决异常后方请求放行新代际。
- **前台限流**：公开收银台与订单查询接口具备独立的内存防刷限制，参数见 `internal/server/read_limit.go`。

## TON 数据提供商信任边界

- **接口依赖**：TON/GRAM 收款以 Toncenter v2 交易 BOC 与执行状态为基础，交叉验证 Toncenter v3 交易主链索引及主链区块高度（`mc_block_seqno`）。
- **信任模型**：两路数据源均来自 Toncenter 服务，当前系统信任其规范链索引，不包含本地独立全节点的验证者签名证明。BOC 验证通过不应表述为独立校验了整条 TON 主链共识。
- **原生代币定义**：本系统的 GRAM 严格指代 TON 网络原生代币（Native Coin），行情读取 Kraken 的 `TONUSD` 交易对；同名的各类 Jetton 代币合约不属于本系统的原生代币收款范围。
