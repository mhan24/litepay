# 可靠性加固实施记录

## 第一阶段

起点：38c43c82990a720ea7b175f3a0e72b758bc34cb1，与远端 main 一致。

已用失败测试复现：核销数据库错误后游标仍推进、游标倒退、没有成功扫描也最终关闭订单、缺失/null 历史数组被当作空扫描成功。修复后保留业务拒绝证据，但技术失败和未知事务结果令整轮失败。重复已消费流水返回 false,nil；核销、订单和观察状态继续使用同一事务。

最终过期现在要求平台最近扫描无错误、查询窗口末端覆盖到订单截止时间加宽限期，且历史缺口不影响该订单。等待补扫期间保留绑定档位，不会因墙钟到期被新单占用；异常原因显示在后台订单详情。超过24小时应人工对账（与商户核对后取消或人工入账），不自动重开已终结订单。未受影响的新订单仍可分配其他金额。不能自动确认历史完整的订单可以继续保留异常，而不是伪造过期通知。

游标只表示已成功请求并处理的窗口末端，不保证交易所不再迟报。宽限期是数据延迟假设，需真实账户验证后设置。超过7天自动回溯能力的区间持久记录 gap_start/gap_end，后续成功不清除；实时与积压窗口均限制到6小时。无法安全跨越的 OKX 同毫秒边界仍失败。

测试：注入 incoming_txs 插入失败后重启补扫、观察更新失败回滚整笔支付、历史缺口持久化、游标单调、终结前扫描门禁、未知响应拒绝，并保留原回归测试。

官方接口核查：
- Binance 账户端点 GET /api/v3/account 文档列出 uid，签名 USER_DATA；目标账户权限和 UID 与收款标识的对应仍待真实验证：https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/account
- OKX GET /api/v5/asset/deposit-history：type=3 内部转账，fromWdId 为内部转账来源标记，state=2 充值成功，时间戳 after/before 分页，单页最多100、6次/秒/User ID。ts 是记录创建时间，不等同付款方点击转账的时间；端点对目标 UID 付款方式的实际覆盖与历史保留能力待真实验证：https://www.okx.com/docs-v5/zh/#funding-account-rest-api-get-deposit-history

未访问正式服务器、未使用真实密钥、未进行真实付款。

## 第二阶段

档位改用整数微单位（1e-6）计算并建立平台/币种/整数金额唯一索引；订单保存 pay_units 与建单时精度。旧 float 字段保留作界面及旧内部调用适配，不再用于档位算术；开发库启动时回填整数。交易所原始金额保存为 amount_text，解析与匹配使用有界十进制有理数，Binance 明细总计也不再用浮点容差。HTTP 选择支付使用原始商户金额字符串。修复 1.005 二进制舍入到1.00的问题。

保留现有 BEpusdt 规则：到账金额按订单展示精度四舍五入，因此小于应付金额但修约相等仍可接受（例如99.498匹配99.50）；精度不随配置更新而改变。不是严格逐最小单位等额付款规则。限制金额、长度和整数溢出；无法经商户 JSON 数值往返保持档位的金额拒绝分配。回调仍保持独角数卡所需 JSON number 与自然数值签名，现有验签回归保留。

同商户订单号的 READY 支付约定遇到实质不同请求时明确返回冲突，保持旧支付信息；完全相同重试复用。数据库增加未最终化商户订单唯一约束，不仅依赖进程内锁。付款方式重选保留旧金额冷却；已付款、已取消、已最终化订单仍不能被自动再核销。旧选择下才出现的付款保留为未归属证据，不自动归到其他订单。

## 第三阶段

失败测试复现：租约过期后新 worker 重新领取，旧 worker 返回 SUCCESS，原先仅依靠 notify_attempts/订单状态会覆盖新持有者。每次领取现在生成随机 lease ID，结果回写必须匹配当前 ID，审计日志保留 ID；旧结果仅留审计，不改任务状态。租约长度至少覆盖配置的 HTTP 超时加15秒。保留原有崩溃恢复、失败重试与商户替换串行化测试。

回调仍是至少一次：商户已处理但响应丢失或 ACK 后本地提交失败会重试，必须由商户按网关订单号幂等。没有 exactly-once 保证。
